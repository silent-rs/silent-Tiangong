# 持久化 Subagent 插件需求整理

需求来源：[issue #480](https://github.com/silent-rs/tiangong/issues/480)《设计持久化 Subagent 插件：跨会话激活、统一 Adapter、Hook 回调与生命周期管理》。本文档整理阶段一（最小闭环）的实施范围与关键决策，后续阶段推进时同步更新。

## 目标架构：有状态的长期成员（2026-09-07 用户裁定方向）

Subagent 不是「接任务、执行、返回」的后台执行器，而是**有自身状态、上下文和行动能力的独立 Agent**：

- **成员运行时模型**：主 Agent、其他成员、工具结果与外部事件统一进入**成员自己的消息入口**；成员结合职责、记忆与当前状态理解消息，自行决定执行、调整、等待、协作或回报，并向主 Agent 或其他成员投递消息。任务是成员管理的工作对象，**不是成员的生命周期**——任务完成后身份、上下文与协作关系仍然存在；
- **持续维护的成员状态**：身份与职责、当前目标与任务、执行状态（执行/等待/阻塞/停止中）、协作关系（等谁的结果、向谁回报）、长期经验；
- **长任务不挡消息入口**：成员处理长任务期间仍可接收补充说明、其他会话的新请求、协作结果、控制请求；可关联到正在处理的任务、安排待执行、合并已有工作、说明冲突、恢复等待中的工作——但**不等于每条消息并发启动一轮模型执行**：保留有序的状态更新入口，多任务与后台操作并存且互不覆盖成员状态；
- **消息意图分类**：正式任务 / 补充与纠偏 / 协作请求 / 协作结果 / 进展与异常回报 / 控制请求——成员先判断消息影响哪个任务、如何更新状态，而不是「来一条消息就创建一次独立运行」；任务保存发起方与协作关系，**成员可同时服务多个主会话但不混淆上下文与权限**；
- **停止的三层定义**：① 取消某个任务（不终止成员的其他任务）；② 在某主会话停用成员（解除使用关系，成员本身不退出）；③ 关闭成员运行时（停止整个成员及其后台执行）。中断（SIGINT 等）针对具体执行实例，不默认作为「停用持久成员」的实现；
- **休眠唤醒**：持久身份不等于常驻模型调用——无待处理事件时休眠，新消息或工具结果到达时恢复，控制运行成本；
- **分层职责**：主 Agent 管用户目标、总体规划、跨成员分工与最终验收；Subagent 管自己负责范围内的安排、执行、自修、协作与回报；执行系统管消息可靠送达、任务关联、权限与状态进程管理。

**现状映射（差距见路线）**：持久身份/记忆/指令、会话型消息入口（专属会话天然排队串行、闲时自然休眠）、多任务多运行记录、CLI 活跃运行注入（补充关联）、任务级取消与会话级停用两层停止——已具备；消息意图分类与「补充关联现有任务」的运行语义、成员主动回报通道、成员级协作关系结构化——为待建差距。

## 实现归一

自 0.2.0 起，`plugins/tiangong-plugin-subagent` 是天工唯一的 Subagent 实现。原进程内 `tiangong-plugin-agent-team`、`create_agent` / `dismiss_agent` / `send_message` / `broadcast_message` 工具、旧 Agent Team 扩展页和聊天内 Agent 标签面板均移除；后续能力（天工会话、原生运行时、Claude Code、Codex、OctoLoop）全部以本插件的 Runtime Adapter 方式迭代，不再维护两套身份、激活、任务和生命周期体系。

旧会话中已经保存的 Agent 消息和事件类型保留只读兼容，确保历史内容仍能正常显示；不再支持从旧界面继续控制历史 Agent 实例。

## 阶段一范围

- 创建 Subagent 插件（`plugins/tiangong-plugin-subagent`，插件 id `subagent`）与 `extension.tab` 管理页；
- 官方原生 Rust Sidecar 作为统一交互总线；
- 支持 `~/.tiangong/agents/<agent-id>/{agent.toml, instructions.md, memory/, artifacts/}` 身份目录；
- Agent 列表、会话激活与 Workspace 绑定（含写互斥）；
- 发送消息（`send_agent_message`）与提交任务（`submit_agent_task`）；
- 完成、阻塞、失败 Hook 回调投回激活会话；
- 关键回调先落盘再投递，Sidecar 重启后补投；
- 退出天工时清理 managed 运行实例（attached 只断开）。

### 0.2.0 追加（用户裁定优先级：关联会话后端提前实现）

- **天工原生 Subagent 后端（agent_team，推荐默认）**：系统为 Agent 新建并独占一个专属天工运行时会话——
  - 招募（create_agent）无需任何会话或命令线索，backend 缺省即原生；
  - 首次运行自动新建专属会话并在投递成功后回写绑定，后续任务延续同一会话的上下文（原生 Subagent 的会话记忆）；
  - 执行与回报复用会话后端管线（消息投递 + WASM turn 钩子归因）；专属会话被删则下次运行自动重建；
  - 支持从专属会话整理长期记忆。
- **天工会话后端（tiangong_session，按需使用）**：关联用户已有会话作为 Agent 运行后端——
  - agent.toml 关联 `session_id`；管理页创建时从会话列表选择；
  - 发送消息/提交任务 = 经本机 server 向关联会话投递（消息携带任务目标、Workspace 与 Agent 长期指令/记忆摘要）；
  - **完成回报**：插件 WASM 逻辑层在 `on_turn_finished` 钩子中把「关联会话本轮最终回复」转发给 sidecar，sidecar 将对应 Run 置完成并经 Hook 投回激活会话；
  - 中断/取消 = 向关联会话投递停止通知（尽力语义，无法硬取消宿主内 turn）；
  - 记忆整理来源即关联会话历史。
- **AI 招募（create_agent 工具）**：主 Agent 对话中动态创建持久 Subagent（或复用同名成员），支持 CLI 后端（提供启动命令）与天工会话后端（session_id 或按标题搜索 session_query），默认创建后立即在当前会话激活。
- **memory 长期记忆落成实际功能**：
  - `memory/` 下 markdown 文件可管理（列表/查看/编辑/删除）；
  - 运行注入：CLI 后端 begin 帧、会话后端投递消息均携带记忆摘要（不复制全部会话历史）；
  - 自动归档：Run 完成后把「任务目标 + 结果」追加到 `memory/tasks.md`（结论式记忆）；
  - 从关联会话整理：提取每轮「用户消息 + 最终回复（截断）」生成 `memory/session-notes.md`；
  - AI 工具 `get_agent_memory` / `append_agent_memory` 读写记忆。

不在本版：天工原生 agent-team Subagent 适配（原阶段二其余部分）、Claude Code/Codex 接入（阶段三）、OctoLoop（阶段四）。

### 0.2.6 追加（用户裁定：Sub Agent 互相通信，组成集群协同作业）

- **成员间定向协作消息**：`send_agent_message` 在「发起会话恰好是某个成员的后端会话（专属会话/关联会话）」时识别为该成员发起的集群协作——
  - 目标成员无需在发起会话激活（集群协作不经过主会话激活语义），运行以合成协作激活执行；
  - 运行记录新增 `origin_session`（发起方会话）：完成/失败回报投回发起方会话，主会话发起时保持原行为（投回激活会话）；
  - 运行 Workspace 解析顺序：目标成员最近激活 → 发起成员最近激活 → 存储根默认工作区；
  - CLI 后端同样可被协作（消息经 JSONL 帧注入或新建运行，结果投回发起方会话）。
- **协作语义注入**：工具使用规范与投递正文说明「成员之间可互相发送协作消息，对方完成后回复自动送回发起会话」——各成员后端会话可见同一工具集，构成集群协同基础；投递正文「来自」修正为真实发起方（此前误写为接收方自身）。

### 0.2.7 追加（用户裁定：管理页可查看协助过程，暂不需要一键跳转）
- **事件自动标注发起会话**：集群协作运行的全部事件（run_started / completed / failed / 中断等）payload 自动携带 `origin_session`，无需逐调用点传参；
- **管理页协作观测**：成员详情「最近事件」对协作事件显示「来自 成员名」标注；页面底部新增「协作时间线」——跨成员关键事件按时间正序聚合为「发起方 → 目标成员：动作（摘要）」，主会话发起显示「主会话」；快照事件量 50 → 200 条。

### 0.2.9 追加（用户裁定：特性与记忆具备成长进化能力）

- **经验自主沉淀**：任务/消息投递正文附带成长引导——成员完成工作后把可复用经验（成功做法、踩坑、用户偏好，一行一条结论式）经 `append_agent_memory` 写入 `memory/lessons.md`，跨任务累积；
- **记忆注入按价值配额**：运行注入快照分文件配额（lessons 优先并给予最大份额，其次 notes，任务流水与其余文件填充剩余），避免低价值流水挤掉高价值经验，总量上限不变；
- **指令受控成长**：新增 AI 工具 `append_agent_instructions`——向成员长期指令**追加**新学到的稳定规则（带日期分段，不可覆盖既有内容；单次与总量设上限，超限提示整理）；权限规则：主会话可操作任意成员，成员后端会话只能操作自己（防止成员互改人格）。

### 0.2.10 追加（用户裁定：审查报告后修执行可靠性，先于功能扩展）

**调度规则（设计要求与验收项）**：

- 用户输入 `@成员名` 始终由主 Agent 接收并调度（理解意图、决定派活方式）；输入框 @ 候选只是表达辅助，不切换接收方、不绕过主 Agent 直发；
- 正式任务（submit_agent_task，有目标与完成条件、可跟踪）与补充消息（send_agent_message，对已有工作追加背景/追问/纠偏）语义不同，工具描述已区分；
- 同一成员并发多运行时，投递正文携带「运行标记」，完成回报按标记精确归因（无标记回退最新活跃运行）；
- 成员协作的权限规则与主 Agent 派活一致：写互斥检查照常执行；会话型后端不支持隔离工作区策略，显式拒绝；
- 停用成员时对会话后端运行先投递停止请求（尽力语义）再落中断状态，状态说明如实标注。

**本轮修复（审查报告核实后）**：

- 回报提取仅限本轮（锚点之后），不再引用历史轮次结果（P2-1）；
- 运行标记归因，连续/并发任务不串结果（P1-2）；
- 协作合成路径接入写互斥检查、隔离策略显式拒绝（P1-4）；
- 停用路径补投递会话停止通知（P1-5 部分；真实硬取消需 server 提供取消端点，见下）。

**已知限制（需 server 侧配合，另立项）**：

- 会话型后端（agent_team / tiangong_session）的工作区策略暂不强制：只读成员在专属会话内仍可调用写入工具，投递正文提示是当前唯一约束。落实需 server 支持受限会话创建（绑定工作目录与工具权限）；
- 会话型运行无法硬取消：server 缺少「取消指定会话当前 turn」的 API，当前停止为通知式尽力语义；
- 审查报告 P1-1（服务端另造会话编号）经核实不成立：`POST /api/v1/messages` → `ensure_core` 全程沿用传入 channel_id 创建会话，编号一致。

### 0.2.11 追加（用户裁定：二轮复审后修执行正确性与资源安全）

复审确认六项问题全部属实（含上轮修复引入的两处错误），逐项修复：

- **回复提取**：本轮切片改从锚点之后开始且不再跳过——此前「倒序后跳过一条」恰好丢掉本轮最终答案（P1）；
- **标记归因严格化**：携带运行标记但匹配不到对应活跃运行（迟到回报/重复回报）时直接忽略，绝不回退到其他运行（P1）；
- **协作占用登记**：合成协作激活落盘进统一激活表，后续派活/协作的写互斥检查可见；运行终态（归因/取消/CLI 完成/失败/关闭/孤儿恢复）自动释放登记（P1）；
- **停止语义**：新增 `Stopping` 状态——停用/停止对会话后端运行投递停止请求：投递失败如实上抛且状态与占用不动；成功后置 Stopping（占用由运行维持到本轮收尾归因，激活解绑不失守写互斥）；中断/取消通知投递失败记录告警且语义如实（P1）；
- **写互斥扩展**：占用检查除激活表外同时看活跃运行（含停止请求中）——激活解除但运行未结束期间，写入权不释放（P1）；
- **策略能力统一校验**：`ensure_policy_supported` 在正常激活与协作入口共用——会话型后端拒绝隔离工作区（原因准确），CLI 协作不再被误拒（P2）。

复审撤回确认：上轮 P1-1（会话编号错位）双方核实均不成立。

调度方向（后续阶段，不在本版实现）：按任务特点选择执行方式（简单任务主 Agent 直接完成）、大任务规划驱动按验收推进、错误分级回报、成员协作关联父任务等，待执行闭环可靠后按阶段推进。

### 0.2.12 追加（用户裁定：三轮复审——状态真实、回报归属、资源一致）

**口径修正（复审裁定，不再作为本阶段问题）**：协作豁免发起方（共享写入）与 CLI 协作不创建隔离目录，按已接受的协作方式处理；此前「写入者数不增加」的表述不准确——协作期间发起方与目标成员可能同时写入同一工作区，属当前接受的多 Agent 协作风险。默认后端会话编号错位维持撤回结论。

**三项修复**：

- **取消与停止分离**：会话后端取消 = 「不再需要结果」的裁定 + 「停止请求」投递：投递失败如实上抛（取消未送达）；成功后任务层记录逻辑取消、运行置 Stopping（占用保留），成员会话本轮收尾归因时转 Cancelled 终态并释放占用——本轮回复内容不改变取消裁定。CLI 后端取消在进程退出确认后落终态（即实际停止）；
- **控制回复不冒充任务结果**：归因前置忽略控制通知（【Subagent 控制】开头）触发的回复；回报只认运行标记——无标记轮次（用户在成员会话直接对话等）不归因任何运行，不再泛化为「最新活跃运行」；
- **协作登记回收补全**：CLI 正常退出路径挂释放；启动失败（投递/进程启动失败）回滚协作登记，不留残留占用。

**回报卡片展示方向（方案已定，后续阶段实现）**：Subagent 回报以独立卡片呈现（成员、任务、状态、错误、产出、执行次数），查看类操作直接执行，重试/补充分派等以「请求主 Agent 处理」表达；数据与展示分离——结构化回报（来源/事件编号/任务运行编号/类型/摘要/产出/执行状态）由执行系统维护，插件负责展示且不修改任务状态，插件未加载时文本回退可读。依赖宿主通用消息挂载点（session.message-item / message-action / turn-node）与消息上下文补齐，作为通用插件能力建设（定时任务、构建结果可复用），不增加 Subagent 专用宿主判断。

### 0.2.13 追加（用户裁定：四轮复审——停止确认与状态独立性）

- **CLI 终止以真实退出为准**：terminate 在终止信号与强杀后确认进程实际退出才返回成功；未确认退出返回错误，取消入口不落终态、不释放占用（沙箱拒绝信号场景如实暴露）；
- **控制通知识别收紧**：只匹配正文以【Subagent 控制】开头的控制通知；任务正文任何位置引用该字样仍按运行标记正常归因；
- **关闭与恢复的协作登记核对**：CLI 孤儿运行恢复时标中断并释放协作登记；会话型孤儿保留等待归因（宿主会话不因 sidecar 重启而停止）；退出清理同样释放协作登记；
- **逻辑取消独立于运行状态**：任务已取消后，任何运行状态同步（如停用把停止请求中映射回执行中）不得覆盖取消裁定。

### 0.2.14 追加（用户裁定：五轮复审——CLI 停用收敛为有限中断尝试）

- **温和停止流程**：停用 CLI 运行改为最多 3 次中断尝试（每次 = interrupt 协议帧尽力 + SIGINT 信号，间隔约 1 秒），期间收到退出通知立即停止重试；未确认退出前运行保持 Stopping、占用保留，由既有退出通知路径收尾（停用/取消语义优先于退出码）。强杀与退出确认保留给取消路径的终态裁定；
- **状态三档如实**：停用立即解除调度资格（不再接收新任务）；中断发送结果如实反馈（已发送次数 / 发送失败原因 / 已随退出通知结束）；「中断已发送」绝不表述为「进程已退出」；
- **复审已接受行为归档**：共享写入、CLI 协作不建隔离目录、已取消任务在退出清理时转为已中断——均不再列为整改项，相关说明与实际行为一致。

### 0.2.15 追加（用户裁定：回报 = 成员主动投递，非最终总结抓取）

- **主动回报工具 `report_agent_result`**：成员在执行会话内主动调用，向本次工作的发起方（主会话或协作成员）投递结果——带明确任务归属（关联该成员最新活跃运行）与状态（completed / failed / blocked），终结运行、投递回报、归档经验、释放协作占用一体完成。blocked 为非终态（等待发起方补充）；
- **轮次收尾抓取降级为兜底**：成员未主动回报时，turn 结束仍按运行标记归因收尾，但结果明确标记「[轮次收尾兜底]」来源——主动投递与系统抓取可区分；
- 提示词引导更新为「完成收尾务必调用 report_agent_result 回报，而不是只在回复文本里写结论；回报后再沉淀经验」。

### 0.2.16 追加（用户裁定：消息意图与运行关联）

- **补充消息注入进行中的工作**：send_agent_message（会话型后端）在发起方于该成员上有等待中的运行（本会话派活或协作委托，不含停止请求中）时，消息携带原运行标记投递——整轮按标记归因回原运行、结果合并回报，**不新建执行**；事件记录 supplement。没有进行中的工作时才新建轻量消息往返；
- **正式任务语义不变**：submit_agent_task 总是新建运行——多任务并存，互不混并；
- **CLI 后端**维持进程通道注入（同语义）；**工具描述与提示词**更新：send_agent_message 定位为「补充/纠偏/协作（自动关联进行中的工作）」，正式工作引导走 submit_agent_task。

### 0.2.17 追加（用户裁定：协作关系结构化，目标架构差距③）

- **协作关系视图 `list_pending_work`**：从运行记录派生「谁在为谁执行（按执行成员）」与「谁在等谁的结果（按发起方）」双向视图，含工作目标与状态（停止请求中照列——占用事实）；发起会话归属成员会话的标注发起成员，否则为主会话；支持按成员过滤，返回结构化行与模型可读文本。供主 Agent 安排分工、催办、补派前查询；
- 提示词补充：安排分工或判断进度时先查协作关系视图。至此目标架构三项差距（消息意图关联、主动回报、协作关系结构化）全部落地。

### 0.2.18 追加（用户裁定：七轮复审——回报明确关联与轮次边界）

- **回报明确关联（修 P1 串任务）**：report_agent_result 新增 run_marker——成员同时处理多项工作时按正在处理消息尾部的运行标记精确指明回报对象，缺省才回退最新（单工作场景）；标记不匹配如实报错；
- **轮次结束不替成员决定（修 P1 blocked 被改写）**：成员已明确表态的运行（blocked 等待补充 / 停止请求中 / 待审批），轮次结束仅记 turn_ended 事件、状态保持；只有未表态（working/ready）的运行才由轮次结果收尾——「一轮对话结束 ≠ 成员管理的任务结束」；
- **取消裁定不被回报覆盖（修 P1）**：停止请求中的工作收到成员成果时转「备查」——终态 Cancelled 保持取消裁定、成果留存于摘要并作为消息转达发起方，不恢复为正常完成；
- **补充修订链（修 P1 修正丢失）**：补充消息排在原轮次之后（服务端串行）导致原运行已终结时，同标记的补充轮作为**结果修订**：更新原运行结论（[含补充修订] 前缀）、记 revised 事件、修订结果重投发起方——修正不丢失；
- **注入不新增资源（修 P2 残留激活）**：补充注入判定前置到任何激活创建之前（含 CLI，按运行归属匹配进程通道），复用工作时以轻量载体投递、不落盘激活记录。

### 0.2.19 追加（用户裁定：协作按 workspace 域隔离）

- **协作 workspace 绑定发起会话**：协作运行的 workspace 域取发起会话（发起成员专属会话）的 cwd——不同 workspace 的协作链互不漂移；发起会话无有效 cwd 才回退目标/发起方最近激活，最终回退 home。补充注入的轻量载体同规则；
- **视图标注 workspace 域**：list_pending_work 的双向视图与结构化行携带 workspace——跨工作区的等待关系可区分；
- 写互斥本就按 workspace 精确比较：W1 的独占写不拦 W2 的写入（跨工作区并行合法），同工作区互斥不变。

### 0.2.20 追加（用户裁定：总线矩阵测试与 MCP server 能力）

- **MCP server（v0.2.21 起无参数、首帧自动探测）**：sidecar 以标准 MCP（stdio JSON-RPC）对外暴露总线——外部 agent 工具（Claude Code、Codex 等）可直连：activate/deactivate、send_agent_message（补充自动关联）、submit_agent_task、report_agent_result（标记关联）、list_pending_work（协作视图）、运行控制与记忆读写，共 13 个工具；与宿主走同一分发与状态机（单一真相源），MCP 调用方以固定外部会话身份执行（回报投回其发起关系）；同步返回操作结果提供快速消息反馈，回报与状态可经查询工具拉取；
- **message bus 矩阵测试**：消息类型全集（任务/补充注入/协作/协作补充/主动回报/补充修订/控制中断）在一次会话中顺序流转，逐步核对运行、事件（supplement/revised/completed）、激活登记与释放、协作视图一致性（视图行数=活跃运行数）四层记录——总线行为回归有系统性基线。

### 0.2.21 追加（用户裁定：MCP 无参数化与管理页配置参考）

- **首帧协议探测**：sidecar 启动即同时支持两种协议——预读首帧判定，JSON-RPC（jsonrpc+method）进入 MCP 循环，宿主 IPC 帧回喂原生 stdio 循环（共享库新增 run_stdio_with_first_line 首帧回喂入口），不再需要 --mcp 参数；
- **管理页配置参考**：Subagent 管理页新增「外部工具接入（MCP）」区块——展示可直接复制的 mcpServers 配置片段（sidecar 路径、存储根、Server 地址占默认值并注明以实际为准）。

### 0.2.22 追加（用户裁定：八轮复审——消息归属与多实例边界）

- **多实例所有权（修 P1）**：MCP 接入层构造跳过启动恢复——恢复是执行管理者（宿主实例）的职责，外部接入不得把其他实例正在执行的运行误标为遗留中断；
- **无标记回报拒绝歧义（修 P1）**：成员有多项等待工作时，回报必须携带 run_marker，缺省仅在恰好一项时合法——总线不猜测归属；
- **修订归属校验（修 P1）**：补充修订只匹配本会话所属成员的已完成运行——跨成员完善须先建立协作关系，不能仅凭标记后缀接受修改；
- **任务结论同步（修 P2）**：修订更新运行结论的同时同步任务 result_summary——运行与任务引用一致；
- **外部回报协议收窄（复审口径）**：MCP 清单移除 report_agent_result（外部发送者/接收者/任务绑定协议后续接通，不放宽内部身份校验）；**MCP 错误映射（修 P2）**：业务失败如实置 isError=true 并保留原因。

### 0.2.23 追加（用户裁定：外部 MCP 回报协议接通）

- **外部凭据回报 `report_run_result`（MCP）**：外部执行体凭任务消息尾部的运行标记关联工作——标记只在投递正文给出，收到任务的一方才持有（凭据语义）；验证运行存在且未终结后与内部回报走同一收尾核心（终态化、事件、Hook 投递发起方、归档、协作释放、取消备查语义一致）。重复、迟到、伪造标记一律拒绝；
- **回报核心共用**：内部成员会话回报（身份=会话归属）与外部凭据回报（身份=运行标记）经同一 finalize_report 收尾——语义单点维护；
- 至此八轮复审六项全部关闭；外部身份完整声明（发送者/接收者/消息类型字段化）与消息卡片仍为后续方向。

| 插件形态 | schema v2：manifest 声明工具 + extension.tab + resident Rust sidecar，工具直连 sidecar | terminal 同款成熟形态 |
| 首版运行后端 | CLI Adapter（JSONL 非交互协议子进程，managed 进程组）；0.2.0 追加天工会话后端（WASM turn 钩子回报完成） | issue 接入优先级第 2 层；同时是阶段三 Claude Code/Codex 的地基 |

| 运行态持久化 | `~/.tiangong/agents-runtime/`（activations、tasks、runs、hooks 队列、worktrees） | 高频运行状态不写入 agent.toml |

| Workspace 策略 | read-only / read-write-exclusive（写锁表强制互斥）/ isolated-worktree（git worktree） | 读可并行、写有明确所有权 |

## CLI Adapter JSONL 协议（首版）

- sidecar 以 `sh -c <command>`（Windows `cmd /C`）启动子进程，cwd 为绑定的 workspace（或独立 worktree）；子进程留在 sidecar 进程组内（宿主退出时级联清理）；
- stdin 每行一个 JSON：`begin`（含 agent/activation/task 信息）→ 后续 `user_message` / `interrupt` / `cancel`；
- stdout 每行一个 JSON 事件：`message` / `status` / `blocked` / `approval_required` / `completed` / `failed`；非 JSON 行按 `message` 处理；
- stderr 收进 run 日志；协议要求子进程在 stdin EOF 时自行退出（宿主异常退出的级联兜底）。
