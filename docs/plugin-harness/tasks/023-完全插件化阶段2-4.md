## 阶段 2：终端完全体（PTY 移入 sidecar + xterm.js 进 shadow）

### 架构

```
plugins/terminal-handler/
├── sidecar/（Rust，插件自带原生进程）      ← 复用 tiangong-plugin-sidecar 框架
│   └── PTY 会话管理（portable-pty）：
│       spawn/write/resize/kill/read 增量输出缓冲
├── src/shell.ts（工具执行：tool.requested → bridge sidecar.* → tool.resolve）
└── src/TerminalView.vue（xterm.js 渲染，挂 extension.tab shadow 容器）
```

### 依赖的三块基建

1. **桥接 sidecar.\* 通道**（已完成）：TS 插件经
   `bridge.call("sidecar.<operation>", payload)` 调用本插件 sidecar，
   复用 `registry::invoke_sidecar`（签名/启动/协议握手全部沿用现有机制），
   权限 `sidecar.invoke`。
2. **sidecar 通知事件通道**（待做，通用基建）：sidecar service 主动推送
   通知（PTY 输出流）→ 传输层写回宿主 → runtime 转 bridge 事件
   （`sidecar.event`）→ 插件 UI。需扩展 `tiangong-plugin-sidecar` 框架
   （当前仅请求-响应）与 runtime 侧事件泵。
3. **xterm.js in shadow**（待验证）：纯 JS 可跑 Shadow DOM；需实测
   resize/焦点/性能；UI→PTY 输入经 `bridge sidecar.terminalWrite`。

## 阶段 3：webview 容器原语（宿主通用，非浏览器特化）

宿主提供第四种声明式容器（与 shadow/iframe/native 同级，设计文档 12.4）：

```
容器接口（中立原语）：
  create(url, opts) → view_id        创建 webview 实例（宿主进程内）
  navigate/eval/resize/hide/close
  事件：page.loaded / console / dom.ready / screenshot
```

- 声明方式：UI 贡献 `sandbox: "webview"`（或容器声明块）
- 权限：`webview.use`；实例生命周期归插件管理
- 现有 `tiangong-plugin-browser` 的 manager/watcher 演化为该原语的宿主实现
  （通用化：去浏览器业务语义，保留 webview 引擎管理 + CDP 路由）

## 阶段 4：浏览器完全体

```
plugins/browser-handler/
├── 工具声明（browser_open/navigate/eval/snapshot…）
├── TS 逻辑：tab/会话路由、agent 协作策略、观察策略
└── UI：地址栏/工具栏（shadow）+ 声明 webview 容器实例
```

宿主残留：webview 引擎原语（声明式，中立）——如同 iframe 容器，非业务。

## 边界与风险

1. sidecar 通知通道是通用协议变更（传输层双向化），需向后兼容存量 sidecar。
2. xterm.js 在 shadow 的 DOM 测量兼容性待实测；不达标则降级 iframe 容器。
3. webview 原语化需重构现有 browser crate（manager/watcher 去业务化），
   建议在原语稳定前保留旧通道双轨。
