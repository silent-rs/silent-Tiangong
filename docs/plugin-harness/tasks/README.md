## 3. 依赖与并行关系

- **必须串行**：T001 → T002 / T003 → T004 → T005；T006 → T007 → T008 → T009/T010。
- **可并行**：
  - T002 与 T003 只共享 T001，不共享未完成代码，可并行。
  - T009 与 T010 共享 T008 完成后可并行。
  - T011 / T012 / T013 之间可并行（各自迁移不同内置能力）。
  - T014（审批）与 M1 的 T006-T010 可并行（只依赖 T003）。
- **解除阻塞**：T005 完成标志 M0 可交付；T010 完成标志 M1 能力矩阵可交付；T011-T013 完成标志内置能力插件化可交付。
- **验证任务**：T005 是纯验证任务，不引入新功能；它若发现设计不一致，回改 T002-T004 的 spec，不向下游扩散。

## 4. 拆分原则与约束

1. 每个任务只改一个主要边界（数据模型 / 清单解析 / 后端命令 / 前端外壳 / 前端容器 / 内容组件 / 内置迁移 / 验证）。
2. 每个任务独立提交、独立验证；不把 UI + 后端 + 权限 + 端到端验收塞进一个任务。
3. 后续任务不要求修改前置任务的完成标准；发现冲突先回改对应 spec，再继续。
4. M2 及之后的任务 spec 在 M1 完成后再逐批细化（当前只给出目标与依赖，避免过度设计）。

## 5. 首批任务（M0）交付说明

M0 的 5 个任务（T001-T005）已具备完整 spec，可直接开始开发。它们共同完成「接缝地基」：定义类型与注册表、解析新清单、打通桥接命令、用设置页 Slot 验证旧插件经新桥接渲染，形成可回滚的最小闭环。

详见各任务 spec 文件：

- `001-核心类型与注册表.md`
- `002-manifest-v2解析校验.md`
- `003-宿主桥接命令层.md`
- `004-设置页Slot容器.md`
- `005-端到端验证.md`
