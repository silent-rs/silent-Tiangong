# 07 - 只读工具并行执行设计

## 目标

设计安全的只读工具并行执行策略，为后续提升 Agent 复杂任务执行效率做准备。

## 范围

- 工具元数据分类
- 工具执行调度策略设计
- ReAct 工具执行阶段设计
- 权限审核与并行执行关系
- 失败隔离与结果排序规则
- 后续实现任务拆分

## 依赖

- 前置任务：04、06
- 后续任务：无
- 可并行任务：无
- 阻塞说明：04 未完成前，工具执行阶段没有清晰边界；06 未完成前，并行失败隔离缺少结构化基础。

## 任务

- 定义工具副作用分类：
  - 只读工具
  - 文件写入工具
  - 命令执行工具
  - 浏览器交互工具
  - 数据库写入工具
  - Agent 团队管理工具
  - 调度器变更工具
- 明确哪些工具允许并行，哪些必须串行。
- 明确权限审核发生在并行调度前还是调度中。
- 设计并行结果排序：保持模型 tool_call 顺序写回，还是按完成时间写回。
- 设计并行失败隔离：一个工具失败不能取消其他安全工具，除非属于同组强依赖。
- 设计并发上限和 token/输出预算。
- 拆分后续实现任务 spec。

## 工具副作用分类

| 分类 | 工具/来源 | 默认调度 | 原因 |
|---|---|---|---|
| 只读文件/代码查询 | `read_file`、`list_dir`、`tree_dir`、`search_code`、`get_skill_detail`、`current_time` | 可并行 | 不修改会话外部状态；结果可独立写回 |
| 只读检索 | `recall_memory`、`index_search` | 默认串行，后续可有限并行 | 依赖当前上下文和单轮去重策略；`recall_memory` 当前有单轮只执行一次语义 |
| 只读网页/浏览器查询 | `web_fetch`、`web_form_extract`、`web_query_dom`、`web_locate_element` | 默认串行，后续按会话/Tab 加锁后可并行只读快照 | 浏览器工具共享活跃页面和事件队列，`web_fetch` 可能打开页面，不是纯只读 |
| 文件写入 | `write_file`、`replace_in_file`、`apply_patch` | 必须串行 | 修改文件系统，受文件锁、审计和结果顺序影响 |
| 命令执行 | `run_command`、`run_shell`、`terminal_send` | 必须串行 | 命令可能读写任意状态、占用终端、依赖 cwd/env 和前一条命令输出 |
| 浏览器交互 | `web_form_fill`、`web_click`、`web_load_html` | 必须串行 | 会改变页面状态、焦点、导航和事件队列 |
| 数据库/调度器写入 | `scheduler create/update/delete/trigger`、后台任务 `spawn_task/cancel_task` | 必须串行 | 修改持久化调度状态或后台任务状态 |
| 多媒体生成/转换 | `generate_image`、`generate_video`、`text_to_speech`、`speech_to_text` | 默认串行，后续可按资源预算并行 | 请求成本高、输出大、可能触发文件归档和任务状态变更 |
| Agent 团队管理 | `create_agent`、`dismiss_agent`、`send_message`、`broadcast_message`、`notify_user`、`lock_file`、`unlock_file` | 必须串行 | 修改团队状态、消息队列、文件锁和用户通知 |
| MCP 工具 | 所有动态 MCP 工具 | 默认串行，只有显式声明只读后可并行 | 当前 MCP 元数据缺少副作用声明，未知工具按 Critical 处理 |
| 未知工具/插件覆盖工具 | 未在元数据表内的工具 | 必须串行 | 无法证明无副作用 |

## 并行/串行决策规则

1. 只有同时满足以下条件的工具调用才允许进入并行组：
   - 工具副作用分类为“只读文件/代码查询”。
   - 权限决策为 `Approved`，不需要用户审批。
   - 参数解析成功，且没有 `__parse_error`。
   - 不依赖前一个工具的输出；模型同一批 tool_calls 中没有显式顺序依赖标记。
   - 不访问同一个可变外部资源锁，例如浏览器活跃 Tab、终端、文件写锁、团队状态。
2. 以下工具即使看似读取也默认串行：
   - `web_fetch`：可能打开/导航页面，改变浏览器状态。
   - `recall_memory`：当前单轮有去重和恢复策略，不能并发重复调用。
   - `index_search`：可读但可能有内部索引状态和 token usage，需要先单独评估。
   - MCP 工具：除非 metadata 明确声明 `side_effect = "read"`。
3. 如果一个批次里同时存在串行和可并行工具：
   - 保持模型 tool_call 顺序切分为多个 segment。
   - 连续的可并行只读工具组成并行 segment。
   - 串行工具单独作为 segment。
   - 后一个 segment 必须等待前一个 segment 的结果写回后再执行。

## 权限审核设计

- 权限审核发生在调度前，而不是并行任务内部。
- 调度前先对每个 tool_call 做参数解析、重复成功/失败检查、权限判断、审计目标推断。
- 任一工具需要审批时，该工具所在 segment 暂停；已完成的前置 segment 结果保留，后续 segment 不启动。
- 审批通过后继续执行该工具所在串行 segment；审批拒绝写入结构化失败并结束或重新规划，沿用当前语义。
- FullTrust 只影响权限放行，不改变副作用分类；命令、写文件、浏览器点击仍不因 FullTrust 自动并行。

## 结果排序与写回

- 并行执行可以按完成时间收集内部结果，但写回 session 和发送模型可见 tool result 时必须保持原始 tool_call 顺序。
- `StreamEvent::ToolStart` 可按启动顺序批量发送；`StreamEvent::ToolResult` 建议也按原始顺序发送，避免前端和模型上下文顺序不一致。
- 每个工具结果仍使用原始 `tool_call_id`，不合并多个结果为一个 tool result。
- Token usage、媒体归档、Memory 候选评估按写回顺序处理，避免统计和上下文摘要出现乱序。

## 失败隔离设计

- 并行组内单个只读工具失败不取消其他已启动只读工具。
- 每个失败工具都写入 06 定义的 `[tool_failure]` 结构化记录。
- 并行组完成后统一判断是否需要失败恢复提示：
  - 如果至少一个失败且至少一个成功，模型应优先使用成功结果，并针对失败项重新规划。
  - 如果全部失败，触发当前失败恢复提示。
  - 如果失败类型为权限拒绝或用户拒绝，不自动重试。
- 只有以下情况允许取消同组剩余任务：
  - 用户主动 Cancel/Shutdown。
  - 调度器检测到同组工具存在同一外部资源强依赖，但这类工具本不应进入并行组。

## 并发上限和预算

| 项 | 建议默认值 | 说明 |
|---|---:|---|
| 单个并行 segment 最大并发 | 4 | 防止大量 `read_file`/`search_code` 同时冲击 IO |
| 单个工具模型可见输出上限 | 沿用现有工具结果截断策略 | 完整结果仍可进运行日志或本地文件，模型只看预算内内容 |
| 单个并行 segment 模型可见总输出上限 | 后续实现时新增，建议 24K chars 起步 | 超出时按工具顺序截断并提示 |
| 并行任务超时 | 不新增统一超时 | 沿用工具自身超时；避免破坏长读操作 |
| Memory 候选评估 | 写回阶段逐条执行 | 保持当前顺序和计数语义 |

## 为什么这些工具默认不并行

- 浏览器点击、表单填写、HTML 加载会改变页面状态和焦点；并行执行会导致事件队列、导航和 DOM 状态不可预测。
- 文件写入和补丁应用会修改同一工作区；即使路径不同，也可能影响构建、索引、文件锁和后续工具的读取结果。
- Shell/终端命令可以任意读写文件、启动进程、修改环境或依赖前一条命令状态，不能通过工具名证明安全。
- Agent 团队工具会改变消息队列、文件锁、子 Agent 生命周期，必须保持因果顺序。
- MCP 工具来自外部服务，当前缺少统一副作用契约，默认并行会把风险外包给未知实现。

## 本任务结论

本任务只完成设计，不改变当前工具串行执行行为。后续实现必须先落地工具副作用元数据和 segment 切分，再逐步启用只读本地工具的有界并行。

## 不做

- 本任务只做设计，不实现并行执行。
- 不改变当前工具串行行为。
- 不修改工具 schema。
- 不引入新的异步运行时。
