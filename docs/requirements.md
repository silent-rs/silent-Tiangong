## Sandbox 自管理与独立发布

### 必须满足

1. Sandbox 自身提供 `check-update` 与 `update`，宿主不重复实现下载、验签、自检和 active 切换。
2. 更新只接受 HTTPS 官方清单，执行大小限制、SHA-256、内置官方公钥验签和候选真实自检。
3. 候选协议和首版策略 Schema 与当前 Sandbox 精确相等；版本必须严格递增。
4. 升级使用跨进程锁、独立事务目录、同目录事务文件和程序/签名原子替换，不覆盖正在运行的程序。
5. 更新目标是当前可执行文件；指定目录时只安装标准程序和签名，不创建版本仓库。
6. 发布仅来自 main，标签版本等于 crate 版本，生产发布串行且线上版本严格递增。
7. Linux x86_64、macOS aarch64、macOS x86_64、Windows x86_64 四平台最终制品必须经验签和自检。
8. 0.1.0 由官方发布链 bootstrap；后续版本可由 Sandbox 自身升级。
9. 首版发布前官方 `latest.json` 可以明确返回 HTTP 404：本地 Launcher 已通过签名、版本、协议与真实自检时继续使用本地版本且不发起获取；0.1.0 正式发布前新增兼容策略字段时保持首版策略 Schema 不变，通过重建和重签本地同版本 Launcher 更新；本地无有效版本且远端仍为 404 时沙箱功能保持不可用，但不得阻塞对话与浏览。

### 非目标

1. 本任务不接入 App 设置页或 Tauri 更新界面。
2. 不实现任意版本选择、降级或非官方镜像信任。
3. 不迁入插件注册表、会话工作区或 Sidecar 生命周期管理。

# 需求整理

## 修复沙箱 stdio 中止阻塞（P0）

### 背景

沙箱 stdio 当前会在 sidecar 主循环中等待长请求完成，宿主取消又缺少请求级协议和完整关联，导致停止被同一长任务、会话锁或界面命令线程阻塞。用户点击停止后，界面还可能提前显示空闲，而目标命令和子进程仍在后台运行。

### 必须满足

1. stdio sidecar 必须并发分发普通请求，主读取循环不得等待长请求结束；普通请求设置明确并发上限，取消控制帧不受该上限影响。
2. 协议必须支持按 sidecar 请求编号取消，并由宿主记录会话、工具调用与 sidecar 请求的关联；取消只影响目标请求，不得终止仍承载其他请求的常驻插件。
3. terminal、command 及所有可能启动子进程的官方 sidecar 收到取消后，必须结束目标命令及其全部子进程，并释放 PTY、锁、句柄和会话占用；连续取消保持幂等且不遗留进程。
4. 活跃 turn 的中止必须立即投递到其命令通道，不得先等待会话锁；仅当用户消息正处于发送准备阶段时，允许等待该发送完成后重试中止。
5. 思考强度切换只更新目标会话及其当前活跃 turn，不刷新其他 Core 或插件；不得跨异步等待持有会话锁，切换后停止仍须立即生效。
6. 所有可能长期等待的 sidecar 调用必须离开界面命令处理线程执行，不能阻塞设置、中止、会话切换或其他短命令。
7. 点击停止后前端立即进入“正在取消”状态；后端确认取消、任务自然结束或明确失败前不得显示空闲。取消响应超过 2 秒时提示仍在后台处理并允许重试；重试必须幂等。
8. Rust sidecar 公共库、Node sidecar SDK 与官方 sidecar 制品必须同步采用同一取消协议版本。旧制品不支持请求级取消时明确要求升级，不得退回 TCP 或无沙箱执行。
9. 响应目标：取消控制帧应在 100 毫秒内完成投递，后端在 2 秒内确认已接纳取消；本机正常目标进程应在确认后 2 秒内退出，超时则升级为强制清理并向界面保留真实运行状态。
10. 验证必须覆盖并发长任务立即中止、目标进程退出、其他请求和会话不受影响、切换思考强度后停止、连续取消无残留，并完成 Linux、macOS、Windows 检查、Rust 检查和前端 `yarn build`。

### 非目标

1. 不以杀死整个常驻插件代替请求级取消。
2. 不以关闭沙箱、退回 TCP 或普通进程作为兼容方案。
3. 不把后台仍运行的任务伪装为已取消或空闲。

## 引导消息直接注入（第二轮）

### 背景

运行中的会话继续发送消息（引导/追加消息）时，`deliver` 方法会先取消当前 turn task，
轮询等待最多 5 秒，然后重新构建 TurnContext 并 spawn 新 turn。这导致：
- 重复触发 `on_turn_finished` / `on_turn_started` 生命周期回调；
- 插件副作用被重复执行（如终端数据反复注入）；
- 取消 + 轮询等待引入额外延迟。

### 必须满足

1. 运行中追加用户消息时，不取消当前 turn task（不重新 spawn）。
2. 不重新触发 `on_turn_finished` / `on_turn_started` 生命周期。
3. 中断当前正在执行的命令/工具/LLM 请求，安全插入 User Message 到当前 Session。
4. 避免重复触发终端数据注入等插件副作用。
5. 消息序列合法性：中断后闭合未完成 tool_calls，再追加 user message。

### 非目标

1. 不改变空闲时（无活跃 turn）的正常 deliver 流程。
2. 不改变审批、工具注入等其他输入类型的处理路径。

## 前端工具调用展示优化（参考 DeepSeek Harness）

### 背景

会话中工具调用的展示目前依赖工具结果文本的正则提取：折叠行只显示工具名和 OK/FAIL，
摘要无法回答"这次调用做了什么"；失败时看不到失败原因；展开后所有工具都是同一种
纯文本样式；运行中状态只有输入框上方的"正在执行"文字提示。参考 DeepSeek Harness
（`deepseek-ai/deepseek-harness`）的工具调用消息形式：每个调用默认一行"图标 + 类别
+ 参数摘要"，整行可展开，失败行直接显示错误首行，展开后按内容类型分卡片，运行中用
轻量扫光动画表达。

### 必须满足

1. 每条工具消息折叠为单行：类别图标 + 类别标题 + 从工具调用参数派生的单行摘要。
2. 摘要按工具类别选择最有信息量的参数字段（命令行显示命令、文件类显示路径、
   搜索类显示关键词）；参数不可得时回退到现有文本提取，不出现空摘要。
3. 失败的工具调用折叠行直接显示错误输出的第一行（错误色），不再只显示 FAIL。
4. 取消工具组组头的折叠包裹（第二级）：组统计为静态摘要行，工具行始终直接列出；
   单条工具行保留自己的展开/收起（第三级），结果到达后默认收起、不自动展开，
   仅用户点击摘要行手动展开；展开后按内容类型渲染卡片——命令执行
   为终端样式块，读文件为带行号的内容块，写文件为写入内容预览 + 结果，其余为
   参数/结果分区卡片；长内容保持截断预览 + 展开全部的现有防卡顿策略。
5. 执行中的工具调用在工具组内显示为运行行（参数摘要 + 轻量动画），结果到达后
   原地变为普通结果行。
6. 历史会话与流式会话行为一致；现有分组折叠（组头统计、轮次完成自动收起）不回退；
   轮次「收起过程」按钮位于过程顶部（展开后无需滚到底部收起）。
7. 前端构建（tsc + vite build）与现有测试全部通过。

### 非目标

1. 不改后端事件协议与消息存储格式（参数配对使用已有的 assistant.tool_calls 数据）。
2. 不引入工具子调用树（天工暂无嵌套工具调用）。
3. 不实现 diff 渲染（后端工具结果不输出 diff，写入类以内容预览替代）。
4. 不改非工具类消息（思考、总结、用户消息）的展示。

## 审批与用户征询插件化

### 必须满足

1. `request_user` 继续作为 Agent 发起审批、确认、单选、多选、文本输入和表单的统一 Tool；Agent Loop 在 Tool Call 边界异步等待唯一 Tool Result。
2. Core 与宿主只负责请求登记、会话归属、绝对截止时间、唯一闭合、审批挑战和授权；具体界面及用户操作由 `capabilities.interaction=true` 的 UI 插件实现。
3. 宿主通过 `interaction.requested` 和 `interaction.closed` 向交互处理器推送统一事件，插件通过 `interaction.resolve` 提交响应；第三方插件不得直接生成授权或执行受保护工具。
4. 响应必须按请求的权威会话路由，不依赖当前正在查看的会话；截止时间后响应必须由后端原子拒绝，审批超时不得产生授权。
5. `approval` 必须显式绑定有效 `approval_challenge`，不得在缺失时自动选择其他挑战。
6. 交互处理器必须能覆盖六种请求类型，展示后端 deadline、到期禁用、提交中禁用，并以 closed 事件作为最终状态。
7. 提供一个纯 UI、强隔离、可本地导入运行的样板插件，并在 SDK 中提供稳定类型与便捷封装，供第三方开发者复制。
8. 没有可用处理器或处理器未响应时安全超时；不能绕过宿主直接恢复 Agent 或产生审批授权。

### 非目标

1. 不把交互插件变成工具执行者或权限裁决者。
2. 不引入常驻 Driver、Agent Inbox、Continuation 或 Rust Future 持久化。
3. 不要求第三方插件使用 Vue/React；标准 HTML/CSS/JS 即可实现。

## 浏览器插件界面与交互对齐

### 背景

浏览器管理界面迁移到 `browser` 插件后，在插件内部重复实现了一套标签栏，没有继续使用 App 拓展区顶部标签；原生浏览器页面的显隐也未可靠跟随顶部当前标签，切换到终端后可能影响终端输入回显。界面样式、状态反馈以及历史、缩放、批注等交互仍需与原内置浏览器保持一致。

### 必须满足

1. 浏览器插件内部不得维护独立标签栏；每个浏览器页面必须直接对应一个 App 拓展区顶部标签，并与终端及其他 App 标签统一混排。
2. 浏览器页面的新建、切换、关闭、标题更新和会话恢复由 App 顶部标签统一处理；关闭标签时同步关闭对应页面，不留下可见或可交互的原生页面。
3. 以 `main` 分支迁移前的浏览器界面为对齐基准，工具栏、地址输入区、空页面和弹层在明暗主题下保持一致。
4. 后退、前进、刷新按钮按当前页面历史和加载状态正确启用、禁用并提供反馈；页面已经正常显示后必须及时结束加载状态，不得继续旋转或被加载时限改成失败页面。
5. 恢复页面缩放及其上下限、百分比显示、双击重置和 `Cmd/Ctrl +/-/0` 快捷键；缩放前正确结束批注状态。
6. 恢复全局历史记录的分页加载、跳转、单条删除和全部清空；弹层打开时不得被原生页面遮挡，关闭后恢复页面位置。
7. 恢复矩形批注的开启、结束、元素提取和结果查看，并正确处理无页面、失败和重复操作状态。
8. 原生浏览器页面的显示、隐藏和位置必须跟随 App 顶部当前标签；切换到终端时不得遮挡终端或阻止终端画面实时刷新。
9. 保持插件化已经具备的会话隔离、关闭重开恢复、Agent 与用户共用页面以及页面位置跟随能力。
10. 浏览器插件、终端插件、宿主前端和相关 Rust 本地检查通过；Desktop 功能由用户验收。

### 非目标

1. 本次不新增原内置浏览器不存在的功能。
2. 本次不引入外部 Chrome、密码自动填充或 Passkey 能力。
3. 本次不重构浏览器引擎或插件公共架构。
4. 本次不保留插件内部标签栏作为兼容入口。

## 桌面输入队列

### 必须满足

1. 会话执行中按 Enter 将当前输入（含附件快照）排入该会话队列并清空草稿，不打断正在执行的任务；slash 命令不入队直接执行。
2. Cmd/Ctrl+Enter 立即投递当前输入：空闲开新轮，执行中作为引导消息追加。
3. 队列条目在输入框上方逐条展示，每条可单独立即引导/发送或移除；投递时若草稿非空，草稿自动转入队首不丢失。
4. turn 结束（runStatus 回 idle）且草稿为空时自动按序放行队首；投递失败回插队首不自动重试；队列投递复用现有发送链路（revision/claim 校验、防重复投递、附件归档）。

6. 队列条目支持编辑：内容（文本与附件）回填到输入框草稿并从队列移除，用户改完按现有按键语义重新入队或直接发送；回填时草稿非空则先转入队首。

### 非目标

1. 队列不做持久化，仅内存态，重启后清空。
2. 编辑回填后重新入队排在队尾，不保留原位置。
3. 不提供上移/下移按钮，排序只通过拖拽完成。

## Command 沙箱执行套壳

### 背景

command 插件会执行 Agent 生成的本机命令。当前执行进程拥有宿主用户的完整文件权限，且工作区来源可能被插件载荷或其他并发会话影响。需要由宿主在每次工具调用边界确定工作区，并通过随 App 发布的 Launcher 强制应用操作系统沙箱。

### 必须满足

1. 只有 command 通道启用本功能；每次调用创建独立 stdio sidecar，并恒定经过 `tiangong-sandbox`，失败时拒绝执行。
2. 工作区由宿主的本次工具调用上下文提供，不采信插件载荷中的 `cwd`、`access.workspace` 或进程级全局活跃值。
3. 每次调用创建独立临时目录，只将权威工作区与该临时目录加入写白名单，并设置 `TMPDIR`、`TMP`、`TEMP` 指向该目录。
4. macOS 使用 Seatbelt，Linux 使用 bubblewrap；Windows 当前尚未提供完整的 command 文件隔离，必须明确拒绝执行且不得静默降级。Windows Job Object 只负责清理本次调用的进程，不代表沙箱隔离已经可用。
5. Launcher 只启动宿主指定的已安装 command 插件目录内的普通文件，拒绝符号链接、目录越界和身份不匹配。
6. Launcher 策略使用版本化的宿主内部通道传输，插件不能修改策略；stdio 业务通信保持透明透传。
7. 宿主停止调用或退出时，本次 sidecar、Shell 与未脱离安全边界的后代进程必须被清理；Unix 使用独立进程组，Windows 使用 Job Object。进程清理与文件隔离分别判定，平台能力不足时不得作出更强承诺。
8. Launcher 的内置来源是随 App 发布的固定制品（打包准备跨平台、按目标三元组选择）；在线更新作为独立获取通道按第 16 条执行，两者并存且内置版是回退底线。
9. 真实 Launcher 集成验证必须覆盖工作区内写成功、工作区外写拒绝和专用临时目录可写；环境不支持嵌套沙箱时明确跳过原因。
10. 敏感读取拒绝清单覆盖常见凭据位置（SSH、AWS、GPG、Kubernetes、Docker、Azure、GCP、GitHub CLI、`.netrc`）与天工数据根内的密钥、信任库和模型/MCP 凭据文件；为保证完整 Git 工作流，command 仅对 `~/.ssh`、`~/.config/gh` 获得宿主固定授予的读取例外，两处仍禁止写入，其余凭据位置继续禁读；同时允许读写 `~/.cache` 以保持 Git hook 与工具链缓存可用。工作区位于数据根之下时按敏感件精确拒绝，不遮蔽数据根。
11. 资源上限（CPU 时间、Linux 的内存与进程数）由 Launcher 在启动目标前强制施加并随继承传播，不依赖 sidecar 自觉配合；darwin 不支持地址空间 rlimit，macOS 内存失控由命令级超时与进程树清理兜底。
12. 环境注入防护在 spawn 层与 runtime/file env 注入层同时拒绝动态加载前缀和解释器启动注入类变量（`NODE_OPTIONS`、`PYTHONPATH`、`PERL5OPT`、`RUBYOPT`、`JAVA_TOOL_OPTIONS`、`ZDOTDIR` 等）。
13. 进入 macOS SBPL 的路径含控制字符或非 UTF-8 内容时编译为拒绝一切的 profile（fail-closed）；Launcher 入口对策略路径做平台无关的结构化拒绝，不安全路径不得执行。
14. 用户可在设置中显式关闭按需进程沙箱（全局，默认开启）：开关控制首次实际使用才启动的 terminal、command、解释器及清单声明的按需 sidecar；随 App 启动的预加载常驻服务继续强制沙箱。关闭需经警示确认弹窗，关闭期间输入区信任标识左侧常显红色"沙箱关"警告（点击跳转设置）。OS 沙箱在进程创建时固化，切换开关必须停止现有按需进程，下一次终端操作或工具调用按新状态重建；沙箱状态由 plugin-runtime 宿主执行层自主管理，不进入 TiangongCore、TurnContext 或 Plugin trait；页面直调终端与工具调用共享同一运行时状态。资源上限（CPU/内存）不依赖沙箱照常注入。该开关是用户显式设置且全程可视化，区别于静默降级；沙箱平台能力不可用时的拒绝执行语义不变。
15. Launcher 复用插件信任体系做签名与验签：打包时由 prepare-sandbox 以签名私钥（与插件发布共用约定）签名，宿主每次启动 Launcher 前经验签（内置官方公钥或本机用户密钥任一通过），签名缺失或不匹配一律拒绝；打包无私钥时 fail-closed。本地 debug 构建经 sign-sandbox 重签；CI 使用临时测试密钥，官方发布仍走官方私钥。在线更新、版本切换与回滚策略后置（需先建立可信更新链：不低于应用更新的签名强度、版本单调防降级、策略协议兼容矩阵）。
16. Launcher 使用独立版本序列（与 App 版本无关），在线发布到官方 OSS。运行期只完成 HTTPS 下载、SHA-256 校验、内置官方公钥验签、版本目录落位和 `pending` 登记，不停止 Sidecar、不修改 `active`、不热切换；本地无有效版本时允许准备与编译基准相等的官方版本，已有版本只接受更高版本，并在写入前复核当前 `active/pending` 防止旧候选覆盖新版本。下次重启整个桌面应用后，宿主必须在插件预加载及任何 Sidecar 创建前再次验签并运行真实自检，确认版本、协议与策略 Schema 后原子切换 `active`；失败保留旧有效版本，无旧版本时 fail-closed。详细方案见 `docs/sandbox-launcher-restart-activation-plan.md`。

17. 命令环境变量屏蔽清单必须通过设置页 Modal 管理：设置页只展示配置数量与“管理”入口；Modal 使用本地草稿，支持每行一项并兼容中英文逗号，变量名按 `^[A-Za-z_][A-Za-z0-9_]*$` 校验、大小写不敏感去重；取消不保存，保存失败不丢草稿，非法项不得静默丢弃；沙箱更新入口与该清单管理在界面上分离。

### 应该满足

1. 沙箱拒绝以结构化错误返回，便于 Agent 调整命令或向用户说明。
2. 自检只创建和清理本次专用资源，不修改其他应用或系统的临时文件。
3. 三个平台分别验证父进程结束后的调用进程清理行为。

### 非目标

1. 不实现插件信任分级、本地确认或开发者放开模式。
2. 不实现无沙箱审批升级、会话内授权或全权重试；用户级"按需进程沙箱"开关按第 14 条显式设置交付，不属于静默退化通道。
3. 不实现工作区快照、回滚与单文件恢复。
4. 本阶段不迁移 command 以外的存量 sidecar；其它插件由下述“Sidecar 插件沙箱覆盖”独立分支交付。
5. 不实现 Launcher 任意版本切换与手动回滚（防降级）：在线更新只接受更高版本，任何回退的目标恒为随 App 内置的版本；在线获取、验签激活与发布链按第 15、16 条实现。
6. 不防御已明确允许的网络请求产生的远端副作用，桌面端不引入虚拟机。

## 解释器形态 Sidecar 与统一签名信任

### 背景

用户自建插件的常驻能力此前只能经命令通道一次性执行，原生 sidecar 仅对官方签名插件开放。为让用户以熟悉的语言生态（Node/Python）自由拓展天工，插件清单支持声明解释器形态的 sidecar：宿主以白名单解释器运行插件目录内的入口脚本，通道固定 stdio。

### 必须满足

1. 清单以结构化字段声明解释器形态（`sidecar.runtime` 为 `node`/`python` 枚举 + `entry` 入口 + 受限 `args`），不接受命令字符串；解释器由宿主解析（PATH 或 `TIANGONG_NODE_PATH`/`TIANGONG_PYTHON_PATH`），入口必须是插件目录内子目录的相对路径。
2. 解释器 sidecar 只开放 stdio 通道（无监听端口、生命周期与宿主绑定），不走存量 TCP 路径。**统一签名验证**：所有带解释器 sidecar 的插件（官方 / 自建 / 三方）经同一条签名验证路径——签名锚定完整内容清单（content-manifest.json）并做全树双向校验。信任根三类：内置官方公钥（目录分发）、本机用户密钥对（自建链自动使用）、用户手动导入的第三方公钥（本地导入三方签名插件包）。第三方市场 / 目录分发暂不开放（本地导入先行）。签名与遗留本地信任标记不混用（同时存在即拒绝启动）。无有效信任（签名或遗留本地信任）的解释器 sidecar 一律拒绝启动。
2a. 解释器的首次启动时机与其执行脚本的运行周期必须分开处理：Node/Python 解释器只在插件首次实际使用时启动，不随 App 预加载提前拉起；脚本运行周期分为按需（默认，每次调用独立启动并在执行后退出）与常驻（显式声明，首次使用时启动，之后保持运行，支持崩溃换代重启与通知推送）。脚本常驻时承载它的解释器进程同步保持，不能因运行时类型是解释器而在每次调用后强制关闭。
2b. plugin-creator 是**可选官方插件**：不随 App 内置、启动不自动安装或恢复；用户从官方插件目录按需安装，按普通插件规则启用、禁用、卸载（卸载后不得自动装回）与升级。其 devkit 工具链打进自包含 sidecar 产物，页面与 Agent 工具经 bridge `sidecar.devkit.*` 直达；npx CLI 形态保留给终端与 CI。官方发布走完整归档包（含 sidecar/templates/内容清单），签名锚定内容清单。
3. 用户密钥对（自建链）：首次创作安装时自动生成（宿主数据目录 keys 下、权限收紧、原子落盘），宿主在创作链安装时为解释器插件自动签发签名清单（发布者标识 `local`），构建 → 签名 → 验证 → 安装全程免交互（远程 / Agent 自动化闭环）；创作链之外不存在自动签名通道。
3a. **官方信任根唯一且不可配置**：官方插件身份 = `publisher` 为 `tiangong-official` 且经应用内置官方公钥验签成功。不接受环境变量、配置文件或启动参数替换官方信任根；测试密钥不可被识别为官方密钥（签署官方发布者形态的测试插件必须被安装链拒绝）。发布流程在正式发布/部署前强制校验「发布私钥签名 → 内置公钥验签」，不匹配即中止。
3b. 自动签名安装的授权绑定（签名承载的是「已由前置用户行为建立的持续授权」，代码必须确保签名操作确实来自已授权路径）：
    - 用户密钥签名安装能力只授予**官方签名的固定 Plugin Creator**（宿主注入的受信安装方判定，runtime 保持插件中立、未注入即 fail-closed）；其他插件（哪怕声明 `plugin-dev.use` 权限）不可触发用户密钥签名安装。
    - 安装对象必须是**经宿主进程内真实构建登记的产物**：宿主以 sidecar 结果观察者登记官方 Creator 在默认开发根下的成功构建，`plugin-dev.install` 只接受有登记的项目——堵住前端自报插件 ID 冒充安装任意目录内容的通道（非默认根的构建不产生安装资格）。
    - 构建登记**绑定实际产物指纹**（release 内容清单的整体哈希），安装时与暂存副本比对——构建后替换产物（哪怕重算内容清单）无法通过签名安装；仅构建结果 `ok == true` 时登记，失败构建撤销旧登记；安装成功即消费登记（一次构建授予一次安装资格，再次安装需重新构建）。
    - 用户密钥对崩溃残缺自愈：公钥缺失或与私钥不一致时从私钥推导重建；私钥损坏时明确报错，不静默重置信任根；私钥临时文件以 0600 创建（无宽权限窗口）。
    - Shadow 容器只用于界面组织，不作为安全隔离或调用方身份边界；单 WebView 架构下「主窗口内恶意脚本钩取调用参数」属已知边界（后续多 WebView / 独立 IPC 演进项），当前信任链不依赖前端自报身份。
    - 第三方依赖供应链（devkit add 引入的恶意依赖包）不属本信任链范畴，后续经依赖治理单独处理。
4. 第三方公钥导入：仅用户在设置界面手动操作（原生确认 + 展示密钥指纹并提示与开发者公开渠道比对），插件代码、Agent 工具与网页均不得触发导入；发布者标识与公钥一一绑定、重名拒绝，登记表原子落盘且读写串行化，可随时移除，移除后对应插件下次启动即失效。三方插件导入安装时展示权限清单（敏感权限显著标记）由用户确认一次；官方与自建链安装免确认。
4a. 遗留本地信任（local-trust.json）：存量已装插件继续可用（连接与 spawn 前复核语义不变）；新装不再产生本地信任锚，重装 / 升级自动走新签名链。
5. 宿主按 image 清理孤儿进程仅适用于原生二进制形态；解释器形态的进程治理完全依赖 stdio 宿主绑定（EOF/进程组）。
6. Node 协议库（`plugins/sdk-sidecar`，零依赖 .mjs）与插件创作模板（node-sidecar）随仓库交付，与宿主 stdio 帧协议逐字段一致；工具调用经插件页面 bridge `sidecar.*` 命名空间路由。
7. 依赖在构建期解决：node-sidecar 模板为工程构建，esbuild 将入口连同协议库与全部 npm 依赖打成单个自包含文件进 release；安装后的 sidecar 运行时零依赖、零网络、参与哈希锁定。原生 `.node` 模块暂不支持打包。

### 非目标

1. 本期不含 OS 沙箱（解释器档由沙箱覆盖分支叠加）。
2. Python 协议库与模板为后续阶段；第三方市场 / 目录分发解释器 sidecar 为后续阶段（官方目录分发与三方本地导入已在本期交付）。
3. **开发者放开开关（unsafe_mode，RFC 0017 L4）明确不开发**：统一签名信任已提供安全替代路径（本机用户密钥自动签名 / 三方公钥导入 / 测试密钥局部验证）；全局跳过验证的开关削弱信任边界且与官方信任根不可配置原则冲突。早期独立尝试分支（feature/plugin-trust-model 的手工登记模型）已被本体系取代并删除。

## Sidecar stdio 传输铺路

### 背景

"Sidecar 插件沙箱覆盖"要求插件经 stdio 通道进入宿主强制沙箱。为使插件制品可以先行发布、宿主具备传输能力后再逐批启用沙箱，stdio 传输层作为独立阶段先行交付：仅提供通道能力，不包含任何 OS 沙箱执行内容。

### 必须满足

1. 插件侧通用库支持 stdio 通道：宿主 spawn 时以环境变量选择通道，插件业务代码与清单零改动；不注入环境变量时保持存量 TCP 行为完全不变。
2. stdio 帧协议与 TCP 完全一致（首帧认证、请求、响应、进度、通知），流式进度与通知能力在 stdio 通道下保持可用。
3. 宿主侧提供 stdio 连接管理：按插件启动策略预热或懒启动、握手身份校验、请求往返、崩溃后自动换代重启、宿主退出或停止时清理进程组。
4. 工具调用链向 sidecar 传递宿主权威上下文（会话、调用标识、会话工作区），工作区不由插件载荷或进程级全局状态决定。
5. 本阶段所有插件（含 command）继续使用 TCP 通道，App 与插件行为相对 main 无变化。
6. 端到端验证覆盖认证、握手、请求往返、崩溃重启与宿主崩溃后的进程组清理。

### 非目标

1. 不引入任何 OS 沙箱启动、策略或 Launcher 内容（由沙箱覆盖分支叠加）。
2. 不翻转任何插件的通信通道，不处理旧制品兼容识别。

## Sidecar 插件沙箱覆盖

### 背景

command 已具备宿主强制沙箱，但其它带 sidecar 的官方插件仍可能通过存量 TCP 路径以宿主用户权限运行。需要逐个核对插件的文件、网络、平台接口、子进程、长连接和传输需求，并由宿主为每个插件强制应用经过审计的最小策略。

### 必须满足

1. 仓库内全部带 sidecar 的官方插件都必须进入宿主维护的显式策略表；未知插件或缺少完整策略的插件不得启动原生进程。
2. 插件清单不能自行申请或扩大文件、网络、平台接口和生命周期权限，也不增加 stdio 沙箱兼容标记；实际权限与兼容性判断始终由宿主决定。
3. 支持新版 stdio 协议的制品统一经随 App 发布的 `tiangong-sandbox` 启动；宿主通过真实协议握手识别不兼容旧制品并明确拒绝、提示升级，不得退回无沙箱 TCP。
4. 需要工作区的插件必须使用本次宿主调用或当前会话的权威工作区；不同会话不能因共享 sidecar 或 `set_workspace` 覆盖而互相获得目录权限。
5. 固定数据型插件只能写入经过审计的插件数据或应用功能目录；需要读取模型配置、附件或媒体文件时只放行对应受控目录，不放行整个用户目录或整个应用存储根。
6. 网络默认关闭；只有实际依赖外部网络或宿主回调的插件按策略放行。stdio/TCP/PTY、流式进度、通知和长连接能力迁移后必须保持可用。
7. terminal、computer-use、screenshot-input、fs、memory、mcp、scheduler 等特殊插件必须分别验证 PTY、平台接口、动态路径、召回进度、子进程和持续运行能力；隔离能力不足时明确拒绝，不得以普通进程代替。
8. Launcher 必须校验插件身份、清单目标、普通文件、目录边界和制品摘要，且只能启动宿主策略表中允许沙箱化的官方 sidecar。
9. 独立 Sandbox CI 必须覆盖全部策略项、兼容拒绝、真实启动与代表性调用、文件和网络边界、通知或进度、进程清理及打包制品。
10. sidecar 的首次启动时机与启动后的运行周期是两个独立维度：需要全局服务能力且未显式声明运行周期的存量原生 sidecar 保持原有常驻语义，并随 App 启动完成握手；command 继续按每次调用独立启动和清理；terminal 不随 App 启动，在首次终端操作时启动，仅在存在 PTY 会话期间保持，最后一个会话结束后退出；解释器只在首次实际使用时启动，其脚本按清单选择按需退出或常驻复用。创建 Core 或发送首条消息不得重复启动已经预热且仍存活的原生 sidecar。

### 应该满足

1. 固定目录常驻、按会话常驻和按调用临时三种生命周期只在实际能力需要时使用，停止会话或退出宿主后不得遗留进程。
2. 插件升级后首次启动应给出可定位的协议或隔离错误，不把超时伪装成普通业务失败。
3. 三个平台对同一宿主策略采用一致的默认拒绝语义；平台能力差异必须在原生检查中明确展示。

### 非目标

1. 不允许第三方插件通过清单自行获得原生 sidecar 权限，官方签名启动门槛保持不变。
2. 不在本阶段实现插件信任分级、无沙箱审批升级或工作区恢复。
3. 不为动态网络目标建立宿主代理；本阶段需要联网的官方插件按整项网络能力放行，并保留后续收窄风险。

## Windows 沙箱权限隔离

### 背景

Windows 当前只有 Job Object 提供进程树清理和资源限制，尚不能限制文件读取、文件写入和网络。Windows 端只有在这些权限边界真实生效后，才能与 Linux、macOS 一样执行 command 和已迁移 sidecar。

本阶段只完成 Sandbox 与 command 验证，不改动插件代码或插件清单；其它插件在后续独立分支迁移。

### 必须满足

1. 在 Job Object 生命周期与资源限制之外增加 Windows 原生安全边界，默认拒绝用户文件、凭据和网络访问，只放行策略指定的程序、工作区、插件数据目录和本次临时目录。
2. command 与工作区写插件只能写入权威工作区和专用临时目录，且不能修改工作区 `.git`；只读插件不得写工作区。
3. 需要联网的插件只能在宿主策略明确允许时获得网络能力；不需要联网的插件及 command 必须保持断网。
4. Launcher 必须在完整权限策略成功应用后才启动目标；任何令牌、权限、目录授权、网络能力或进程归属设置失败都必须拒绝执行。
5. 子进程必须继承相同文件和网络限制；停止、取消、超时或宿主崩溃后，Launcher、sidecar 及其子进程树全部退出。
6. 临时安全身份、目录授权和系统对象必须按调用清理，不能让后续插件实例重新访问历史工作区。
7. Windows x86_64 原生 Sandbox CI 必须使用真实 Launcher 验证工作区允许写、外部路径和凭据拒绝、`.git` 防篡改、网络允许与拒绝、子进程继承、资源限制和崩溃清理。
8. 完整 Windows 安装包必须包含匹配版本的 Launcher，并在原生运行器上通过隔离自检。

### 非目标

1. 不使用 Windows 容器或虚拟机作为桌面应用的运行前提。
2. 不在 Windows 能力不可用时降级为普通进程，也不以 Job Object 单独代表完整隔离。
3. 不在本阶段实现 Launcher 在线更新、插件信任分级或无沙箱审批。

## plugin creator 自建插件辅助插件

设计文档：`docs/rfc/0017-plugin-trust-and-sandbox.md` §11

### 背景

信任通道与沙箱设施就绪后，需要一个产品化载体让普通用户（经 Agent 对话或创作页面）
自助完成插件"生成 → 构建 → 导入确认 → 迭代 → 诊断"的完整旅程，而非手写文件和命令。

### 必须满足

1. plugin creator 自身为官方签名纯 TS 工具插件（无自有 sidecar），贡献"插件创作"页面与
   `plugin_init / plugin_build / plugin_install / plugin_validate / plugin_logs` 工具集，页面与
   Agent 调用共用同一后端。
2. 写权限经专用受限桥接，路径白名单锁定开发目录（`~/.tiangong/plugins-dev/<id>/`）与只读
   日志目录，不可触达信任库、公钥库与宿主设置。
3. 模板与仓库 `plugins/templates/` 同源：一期提供 ui-app（纯 UI）与 ts-tool（纯 TS 工具，
   参考 interaction）两类；二期提供 ts-sidecar（依赖 launcher 与 stdio）。
4. `plugin_install` 触发宿主导入并进入 L3 原生确认弹窗（能力清单、指纹、破坏性警示）；
   代码迭代后内容哈希变化必须重新确认。
5. 生成规范内嵌工具描述：能力最小化、每个外部依赖注明用途、node 版本门槛、交互类 slot 禁用。
6. plugin creator 不可被 L3 自建（防自举）；其生成的含 sidecar 插件在导入时自动进入继承式沙箱。

### 应该满足

1. 创作页展示项目列表、构建状态、导入历史与确认记录。
2. 构建产物自动生成内容树清单，供 L3 哈希锁定直接消费。

### 非目标

1. 一期不提供 ts-sidecar 模板与可视化代码编辑器（由 Agent 对话编辑开发目录文件）。
2. 不提供插件市场发布能力（分发走 L2 第三方密钥体系，另行设计）。

## 消息列表后台悬停导航（macOS）

### 背景

macOS 只向激活应用派发鼠标移动事件，天工窗口在后台时 CSS `:hover` 不生效，
消息列表右侧导航（用户消息刻度尺与上/下/回底按钮组）无法唤出；且系统首击
只激活窗口、不作用于页面内容。导致"应用在后台时鼠标移到消息列表右侧 →
导航不出现、点击无跳转"。

### 必须满足

1. 窗口未激活时鼠标进入消息列表右侧导航区，刻度尺与按钮组正常显示（视觉与
   激活态 hover 一致，含过渡动画）；移出后隐藏。
2. 窗口激活后由 CSS `:hover` 接管，不残留后台悬停状态。
3. 宿主以轮询全局鼠标位置驱动（macOS 后台窗口收不到鼠标事件），仅在"窗口
   未激活且鼠标在窗口内"时产生事件流量；前端依据导航热区矩形自行判定显隐。
4. 后台悬停同样驱动横条贴近变宽/高亮效果与问答预览卡（复用与真实
   pointermove 相同的内部路径）；预览卡区域有后台桥接保持（后台收不到卡片
   自身的 mouseenter）。
5. 后台首击定位：点击后台窗口的横条或预览卡，激活的同时直接跳转到对应
   用户消息。由宿主检测"从未激活转入激活 + 鼠标刚在窗口内"补发点击位置，
   前端按位置执行跳转（系统首击被窗口激活消费；wry 的 acceptsFirstMouse
   挂在 WKWebView 上，实际接收点击的 WKContentView 不受其控制，不可靠）。
   Cmd+Tab 等无点击激活不误触发。
6. 仅 macOS 生效；Windows/Linux 行为不变。

### 应该满足

1. 采样间隔与位置变化阈值可容忍（50ms / 1 逻辑像素），静止时无重复事件。

### 非目标 / 已知边界

1. 后台热区滚轮不接管：实测后台滚轮不经过应用层事件分发、不派发 DOM 事件，
   pointer-events/overflow 均不影响 WebKit 后台快速滚动的目标选择，应用层
   无法介入（放弃；刻度尺滚轮语义保持既有设计——只翻动边栏）。
2. 坐标转换走 macOS 原生路径：NSEvent::mouseLocation 全局逻辑点 → NSWindow
   convertPointFromScreen → WebView 视图 convertPoint:fromView: → 依视图翻转
   与内容偏移得到页面视口坐标（与 clientX/clientY 同系）；命中判断用 WebView
   实际边界。不枚举显示器、不手动换算缩放（手算路径在负原点/跨屏/混合 DPI
   布局下无法穷举）；AppKit 访问全部在主线程，轮询线程经 in_flight 与超时
   防止任务堆积。
3. Windows/Linux 的后台悬停唤出与首击定位不做。
