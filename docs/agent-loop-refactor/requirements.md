# Agent 执行核心重构 — 需求与行为契约

> 2026-08-14 简化修订：本文件取代“完整复刻旧 Loop 行为后再逐步优化”的目标。已完成的旧阶段工作保留为历史实现基础，但不再把 Summary、ForceFinal、外层续作次数和自动下一轮后台任务视为目标架构。

## 1. 背景与问题判断

当前重构虽然把分散活动状态收拢为 `ExecutionPhase`，但仍完整保留了旧 Loop 的 Summary、ForceFinal、续作次数和多阶段完成判断，并为终态封口后的自动下一轮交接增加了临时队列、一次性后台任务及补偿分支。

结果是：

- Loop 的控制概念由旧名称迁移到新阶段，但没有真正减少；
- 顶层阶段同时表达模型、工具、审批、压缩和完成策略，职责过重；
- 下一轮交接存在旧 Session 快照、重复启动、失败后无人继续调度和关闭时静默丢弃等风险；
- 测试大量固化旧内部策略，无法证明新架构已经替代旧控制模型。

本轮目标改为：**先缩小 Agent Loop 的职责，再围绕公开行为重建输入、取消和交付边界。**

## 2. 总体目标

1. Loop 主干只负责“请求模型 → 执行工具 → 再请求模型”。模型未输出工具调用时只形成**候选完成**，必须经过确定性的完成门控：当前任务没有未满足的工具义务才允许提交。
2. Agent 对外生命周期只暴露 `Idle | Running`；模型等待、工具执行、审批和压缩不再作为 Agent 顶层状态。
3. Agent 自己拥有跨 turn 的 `next_turn` 与 `next_step` Inbox，由一个长期 driver 顺序消费。
4. 使用 `wake_requested` 锁存取消收敛窗口内的唤醒，不为每条消息创建一次性后台任务。
5. Session 保持唯一权威数据源；新 turn 必须在真正启动时读取最新 Session，不提前构造未来上下文快照。
6. 压缩、审批、请求重试和失控预算移出 Loop 主干，分别落入请求策略、工具流水线或生命周期策略。
7. 以用户可见行为和生命周期契约组织测试，删除只用于保护旧 Summary/ForceFinal 控制流的测试。
8. 在不改变现有 Session 落盘格式和插件对外契约的前提下完成等价实现。

## 3. 核心需求

### 3.1 最小 Loop

- **ALR-001 单一 Driver**：同一 Agent 实例至多有一个 driver 消费 Inbox 和推进执行，不允许每条消息各自创建下一轮调度任务。
- **ALR-002 最小循环**：一个 step 只做请求前处理、模型调用、消息记录和工具调用判定；有工具则执行并进入下一 step；无工具时进入候选完成门控，而不是直接提交。
- **ALR-003 候选完成门控**：模型响应不包含工具调用只是候选完成信号。只有 Inbox 没有待处理 `next_step`，并且 `TaskContract` 不存在未满足的工具义务时才能完成；不再额外请求通用 Summary，也不再进入 ForceFinal。
- **ALR-006 工具义务可判定**：执行前从用户意图、入口类型和已知任务上下文建立结构化 `TaskContract`。它只表达可以由程序判定的义务，例如“必须读取指定附件”“必须执行用户明确要求的命令”“代码修改后必须运行验证”“必须取得某个工具结果”，不得依赖另一个自由文本 LLM 判断任务是否完成。
- **ALR-007 工具调用约束**：若 Provider 支持 `tool_choice=required` 或指定工具，且任务当前存在明确工具义务，应在首次请求或修复请求中使用 Provider 原生约束；不能只靠提示词要求模型调用工具。
- **ALR-008 有界协议修复**：模型在仍有工具义务时返回纯文本，必须拒绝该候选完成，并发起有界的工具协议修复请求，明确告知缺少的义务和可用工具。修复次数属于请求错误/协议策略预算，不得演变为 Summary/ForceFinal 外层循环。
- **ALR-009 明确失败而非虚假完成**：修复预算耗尽、Provider 不支持所需工具约束或模型持续拒绝工具时，返回可诊断失败或向用户说明无法完成；不得把未经工具验证的文本标记为成功。
- **ALR-004 顶层状态收敛**：Agent 对外只有 `Idle | Running`。内部可持有当前请求或工具任务，但不得把压缩、审批、完成检查等实现细节扩展为公开生命周期状态。
- **ALR-005 单一执行所有权**：driver 独占可变执行上下文；活动模型和工具任务使用结构化取消并在退出前收敛，不通过多个并列全局 `Option` 推断真实状态。

### 3.2 输入与 turn/step 语义

- **ALR-101 `next_turn`**：后续完整用户请求按 FIFO 进入 `next_turn`；入队后请求 driver 唤醒。每个 turn 开始时最多领取一条。
- **ALR-102 `next_step`**：运行中修正当前意图的输入进入 `next_step`；`steer` 入队并唤醒当前活动，`inject` 只入队、不主动中断。
- **ALR-103 边界领取**：turn 开始时领取一条 `next_turn` 和当时已有的全部 `next_step`；每个后续 step 开始前再次领取 `next_step`，不得提前为未来 turn 构建上下文。
- **ALR-104 同一 Driver 连续处理**：当前 turn 结束后，如果 Inbox 仍有 `next_turn`，由同一个 driver 继续下一 turn，不经过临时全局队列或一次性后台任务。
- **ALR-105 唤醒锁存**：活动取消到 `Idle` 的收敛窗口内若收到新唤醒，设置 `wake_requested`；收敛完成后必须重放唤醒，不能丢失或重复启动。
- **ALR-106 输入语义明确**：调用方必须明确选择 followup、steer 或 inject，不能由封口时序隐式改变同一条消息的语义。

### 3.3 Session、生命周期与交付

- **ALR-201 Session 权威**：Session 是模型历史、消息状态和下一轮上下文的唯一权威来源。现阶段不要求改变落盘格式，但禁止用提前克隆的 Session 快照启动未来 turn。
- **ALR-202 可靠确认**：用户消息只有在以下任一条件满足时才能确认成功：
  1. 已保存并由当前 turn 接管；
  2. 已进入当前 Agent 实例自有、由唯一 driver 消费的 Inbox。

  如果 Agent 正在关闭、Inbox 无法保证后续消费，或封口边界尚不能安全接管，必须明确拒绝；不得先返回成功再静默清除。
- **ALR-203 生命周期唯一**：一个逻辑 turn 只触发一次 `on_turn_started`、一次 `on_turn_finished` 和一个最终终态。
- **ALR-204 最新数据启动**：后续 turn 只能在前一 turn 完成提交后，从最新 Session 和最新运行配置构建上下文。
- **ALR-205 顺序一致**：`next_turn` 保持 FIFO；同一边界批次内的 `next_step` 保持接收顺序；取消、关闭和新输入之间必须有可测试的确定语义。
- **ALR-206 关闭不静默丢消息**：进入关闭状态后拒绝新输入；已确认入 Inbox 的消息必须被处理、持久化为可恢复状态，或向等待中的调用方返回明确失败。当前范围不承诺进程崩溃后的 Inbox 恢复。

### 3.4 工具、审批、压缩与重试

- **ALR-301 工具流水线**：工具调用由独立调度器执行，负责并行上限、独占屏障、模型顺序提交、取消和 Provider tool call/result 协议闭合。
- **ALR-302 审批下沉**：审批是工具执行流水线中的异步服务，等待审批时沿用同一取消信号；Loop 不拥有 `WaitingApproval` 顶层阶段。
- **ALR-303 压缩外置**：正常上下文压力在请求前策略处理；上下文溢出在请求错误策略中压缩并决定重试。Loop 不拥有 `Compressing` 顶层阶段。
- **ALR-304 请求错误策略**：Provider 重试、压缩后重试和不可恢复失败由请求策略返回 `Retry | Fail`；Loop 本身不复制这些判断。
- **ALR-305 预算外置**：不保留 `continuation_count` 或 `max_outer_iterations`。失控执行由外部生命周期/安全策略根据模型调用数、耗时或费用取消；“缺少必需工具调用”的修复使用独立、很小且可观测的 `max_tool_protocol_repairs`，只处理协议违约，不判断一般任务完成度。
- **ALR-306 插件后台保持**：普通 steer 不默认取消子 Agent、浏览器观察、终端监听等插件独立后台任务；显式取消整个 turn 时才执行插件取消语义。
- **ALR-307 义务状态更新**：工具成功、失败、拒绝或取消后必须更新 `TaskContract`；只有成功结果可满足要求成功证据的义务。工具结果必须持久化后，完成门控才能据此放行。

### 3.5 兼容性与可观测性

- **ALR-401 对外协议保持**：现有 Session 落盘格式、StreamEvent、插件公开生命周期和 Provider 工具协议默认不变。
- **ALR-402 用量权威**：模型、压缩重试和工具相关用量按现有契约累计，最终状态使用提交前最新值。
- **ALR-403 结构化日志**：至少记录 session、turn/step 序号、Inbox 操作、driver 状态、唤醒原因、取消原因、工具批次和最终结果；不记录敏感正文。
- **ALR-404 行为测试优先**：测试公开行为、消息顺序、生命周期、取消收敛、工具协议、持久化和用量，不固化无业务必要的内部阶段名。
- **ALR-405 小步可回滚**：Inbox、最小 Loop、策略外置和旧兼容层删除必须分任务实施，每步有独立验证与删除点。

## 4. 明确删除的旧目标

目标实现中删除以下概念：

- `StartCheckingCompletion`；
- `CheckingCompletion`；
- `StartForceFinal`；
- `ForceFinalPhase`；
- `continuation_count`；
- `max_outer_iterations` 及其改名后的等价控制；
- Loop 内独立 Summary/ForceFinal 请求；
- 当前临时 `NEXT_TURN_QUEUE`；
- 每条消息一次性 spawn 的下一轮自动启动任务；
- 未来 turn 的提前 `TurnContext` 或 Session 快照。

删除旧概念不代表删除以下能力：取消、工具协议闭合、审批、压缩、重试、用量累计、持久化、插件生命周期和唯一终态仍是强需求，只是归属改变。

## 5. 测试契约

### 5.1 永久保留

- 直接回答、工具后回答，以及“明确需要工具但模型先返回纯文本”时不会虚假完成；
- Provider tool call/result 配对与顺序；
- 工具并行、独占屏障和取消；
- 审批批准、拒绝、取消和信任模式变化；
- Session 保存、最新消息状态和累计用量；
- turn 生命周期唯一、最终终态唯一；
- 插件反馈、标题、配置和流事件的对外契约；
- 明确取消、关闭和错误恢复。

### 5.2 按新架构改写

- followup 的 FIFO 与同一 driver 连续 turn；
- steer 唤醒并在下一 step 生效；
- inject 不唤醒但在下一自然 step 生效；
- turn 开始和 step 开始的 Inbox 领取边界；
- 取消收敛窗口的 `wake_requested` 重放；
- 前一 turn 提交后才从最新 Session 启动下一 turn；
- driver 抢占竞争中至多启动一次；
- 后台失败后 Inbox 不会变成无人消费状态；
- 关闭时不会静默清除已确认消息；
- 压缩重试与审批等待不改变 Agent 顶层状态契约；
- 普通问答无工具义务时可直接完成；
- 明确命令、附件读取、代码修改与验证等工具义务未满足时，纯文本响应被拒绝并触发协议修复；
- Provider 支持原生工具约束时会启用 `required`/指定工具；
- 修复成功后执行工具并继续，修复耗尽后明确失败且不会发布成功终态；
- 已满足义务不会被重复要求，工具失败也不会被误记为成功证据。

### 5.3 删除或迁移为策略测试

以下旧测试不再作为 Loop 行为契约：

- Summary 触发时机；
- Summary 返回 `NeedMoreWork` 后重新进入 Loop；
- Summary 工具调用是否消耗外层次数；
- 无效 Summary 工具调用的有界迭代；
- Summary 失败后 ForceFinal；
- Summary 与 ForceFinal 双失败；
- ForceFinal 对空回复或非法工具调用的补偿；
- Summary 取消；
- outer iteration / continuation limit 强制最终响应。

仍有独立价值的请求失败、取消、用量和消息落盘断言，应抽离后并入对应公开行为测试，不随旧策略测试一起删除。

## 6. 范围

### 6.1 本轮简化做

- 建立 Agent 自有 Inbox、唯一 driver 和 `wake_requested`。
- 将 Loop 收敛为模型与工具的最小循环，并增加不膨胀顶层状态的确定性完成门控与有界工具协议修复。
- 删除 Summary/ForceFinal 和续作预算兼容层。
- 将审批并入工具流水线。
- 将压缩、请求重试和失控预算移到 Loop 外策略。
- 重新组织测试与模块边界。
- 保持现有 Session 格式和插件外部接口，必要时只增加 core 内部适配层。

### 6.2 本轮简化不做

- 改造 Session 为 DeepSeek Harness 的仅追加事件日志格式；
- 原样复制 Harness 的 TypeScript 包结构或事件名称；
- 改变权限模型本身；
- 重写 Provider 客户端或插件业务；
- 提供进程崩溃后的内存 Inbox 恢复；
- 与 Loop 简化无关的前端或性能改造。

## 7. 量化完成标准

1. `ExecutionPhase` 不再包含通用完成检查、ForceFinal、审批和压缩顶层阶段；工具义务门控是同步决策，不形成新的活动阶段。
2. 代码中不再存在 `continuation_count`、`max_outer_iterations` 及等价的旧双层 Loop 控制；只允许独立且有小上限的工具协议修复计数。
3. 对所有可程序判定的工具必需场景建立 `TaskContract`；未满足义务时，纯文本响应无法发布成功终态。
4. Provider 支持原生工具选择约束时，必需工具场景使用 `required` 或指定工具；不支持时有有界修复与明确失败路径。
5. 删除当前 `NEXT_TURN_QUEUE` 和“每条消息 spawn 一次后台调度”的实现。
6. 同一 Agent 只有一个权威 driver 启动入口、一个 Session 消息写入入口和一个下一 turn 领取入口。
7. 后续 turn 的上下文在真正开始时从最新 Session 构建，不持有前一 turn 运行期间创建的快照。
8. `execute.rs` 只保留 driver 编排；其生产代码必须显著少于当前约 1657 行，目标不超过 1200 行。若因必要协议逻辑未达到，必须给出逐段归属说明，不能以测试增长掩盖主干复杂度。
9. 删除或改写全部旧 Summary/ForceFinal/continuation 策略测试；新测试覆盖 Inbox、turn/step 边界、wake latch、工具义务、协议修复和关闭可靠性。
10. 格式、静态检查、核心测试、相关插件测试和代表性连续交互场景全部通过。
11. 交付前审查确认没有临时双轨、无人消费队列、静默丢消息、虚假工具完成或重复生命周期路径。
