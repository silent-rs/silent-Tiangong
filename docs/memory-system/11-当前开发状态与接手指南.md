## 当前实现总览

### 已落地链路

当前 `memory-system` 已经不是纯文档状态，而是已经接入主运行链路：

1. CLI / Server 启动时调用 `tiangong_memory::ensure_started(...)`
2. Prompt 装配阶段通过 `load_injection_sync()` 读取三级 Injection
3. Core 在 turn 开始前通过 `global_handle().recall_blocking(...)` 做 recall
4. Core 在 turn 结束后通过 `run_micro_rumination_blocking(...)` 触发 Episode 写入
5. Actor 串行协调 `SQLite + Tantivy + Rumination`

### 代码模块现状

## 当前主链路

### 1. 启动链路

- CLI：`crates/tiangong-cli/src/repl.rs`
- Server：`crates/tiangong-server/src/lib.rs`

两者都在进程启动时调用：

```rust
tiangong_memory::ensure_started(workspace_id)
```

### 2. 注入链路

- `crates/tiangong-core/src/prompt/assembler.rs`
- `crates/tiangong-core/src/prompt/sections.rs`

当前 Prompt 装配会读取：

- `~/.tiangong/memory/profile/agent.md`
- `~/.tiangong/memory/workspaces/<workspace_id>/agent.md`
- `~/.tiangong/memory/sessions/<session_id>/agent.md`

### 3. Recall 链路

- `crates/tiangong-core/src/core/mod.rs`
- `crates/tiangong-memory/src/handle.rs`
- `crates/tiangong-memory/src/store.rs`
- `crates/tiangong-memory/src/recall.rs`

现状：

- turn 前会调用 blocking recall
- 默认实际效果是 BM25-only
- Qdrant 路径虽有代码，但没有启用入口

### 4. 写入链路

- `core/mod.rs` 组装 `TurnResult`
- `handle.run_micro_rumination_blocking()`
- `actor.rs -> rumination::process_micro()`
- `writer.rs -> store.write_episode()`
- `db/sqlite.rs + search/tantivy_search.rs`

现状：

- 只有 `had_tool_calls == true` 才会产出 Episode
- Episode 摘要来自最后一条 assistant 消息
- `workspace_id` 已在 `TurnResult` 中显式携带，避免继续串写到 actor 启动时的固定工作区

## 当前问题与风险

### 1. 进程级全局单例设计还没有彻底收口

第二轮 review 中最重要的问题还没真正解决完：

- `ensure_started()` 的并发安全已经通过 `Mutex + OnceLock` 修正
- 但架构上仍然是“每个进程一个全局 Memory Actor”

这意味着：

- 写入路径现在通过显式 `workspace_id` 规避了部分问题
- 但 `load_injection()` / `recall_async()` 仍有 `store.workspace_id` 的兜底逻辑
- 如果将来 GUI / Server 需要在同一进程内同时服务多个 workspace，会继续面临语义混淆

### 2. `TODO.md` 与实际实现已经不同步

当前 `TODO.md` 把大量 Phase B / C 项标记为未完成，但代码里已经有明显落地内容。

这会直接影响后续接手判断，容易让人误以为这些能力还没开始写。

### 3. GUI / 桌面入口尚未看到显式接入

现有 `rg` 结果只发现 CLI / Server 调用了 `ensure_started()`。

如果桌面入口没有单独初始化 Memory，会导致：

- 桌面模式无 recall / rumination
- 文档和实际行为不一致

### 4. IPC / Leader Election 仍是纯骨架

这意味着当前 Memory 仍然是“单进程内可用”，而不是设计文档里的“多进程统一 Memory 服务”。

### 5. Recall 与 Rumination 仍偏“规则版 MVP”

目前尚未实现：

- 真正的 RecallAnchors 提取
- Qdrant 写入链路
- Entity / Decision 抽取
- 基于 lite 模型的 Episode 摘要与结构化抽取

## 建议的接手顺序

### 第一优先级：收口运行时模型

目标：先解决“这套系统在一个长期运行进程里到底如何绑定 workspace”。

建议动作：

1. 决定 Memory Actor 是“全局唯一”还是“按 workspace 分区”
2. 如果保留全局唯一，则所有命令都必须显式携带 workspace/session 上下文，不能再读 store fallback
3. 如果改为按 workspace 分区，则需要把 `global_handle()` 升级为 registry
4. 补齐 GUI / 桌面入口接入

这是最优先项，因为它决定后续 IPC、Qdrant、Meso 是否会建立在错误的抽象上。

### 第二优先级：把 Phase B 真正做完

建议动作：

1. 补齐 SQLite 对 Entity / Decision 的 CRUD
2. 让 EpisodeWriter 输出更完整的 `tool_calls / outcome / importance`
3. 把 IPC + leader election 做成可运行最小闭环
4. 增加至少一组 integration test：
   - turn 完成 -> episode 落库
   - tantivy 可搜
   - workspace scope 正确

### 第三优先级：把 Phase C 从“骨架”推进到“可用”

建议动作：

1. 实现 Episode 向量化与 Qdrant upsert
2. 在启动配置中显式决定是否启用 Qdrant
3. 将 `RecallAnchors` 从原始 query 升级为真正锚点提取
4. 让 `LoadDepth2` 支持定向展开
5. 将 `process_meso()` 升级为真实 Entity / Decision 提取

## 接手结论

`memory-system` 当前不是“从零开始”，而是已经有了可运行的 Phase A 主链路、可用的 Phase B 部分能力，以及大量 Phase C 预埋代码。
