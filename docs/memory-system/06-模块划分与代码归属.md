# 06 - 模块划分与代码归属

## 原则

Memory 系统从一开始就作为独立 crate `tiangong-memory` 实现，不嵌入 `tiangong-core`。

理由：
1. Memory 是跨模式共享的基础设施（GUI、TUI、Server、CLI 都依赖），与 core 的智能体逻辑正交
2. Memory 拥有独立的 Actor 运行时、IPC 服务、Leader 选举等复杂机制，值得独立编译和测试
3. 独立 crate 让各入口（tiangong-cli、tiangong-server、src-tauri）直接依赖 `tiangong-memory`，无需经过 core 中转
4. 避免 core 包含过多基础设施代码，保持 core 专注于智能体编排逻辑

      memory.rs              ← 【废弃】迁移到 tiangong-memory

## 各模块职责详述

### `lib.rs`

crate 入口，导出公共 API：

```rust
pub mod types;
pub mod command;
pub mod handle;
pub mod actor;
pub mod election;
pub mod ipc;
mod store;
mod injection;
mod writer;
mod recall;
mod rumination;

pub use handle::MemoryHandle;
pub use command::MemoryCommand;
pub use election::ProcessType;
pub use types::*;

/// 启动 Memory 系统，返回 Handle
/// 所有运行模式（GUI、TUI、Server、CLI）统一调用此函数
pub async fn start(
    workspace_id: Option<String>,
    process_type: ProcessType,
) -> anyhow::Result<MemoryHandle> {
    MemoryHandle::connect_or_spawn(workspace_id, process_type).await
}
```

> 外部 crate 只接触 `MemoryHandle`，不直接访问 `MemoryStore`。
> Store、Writer、Recall 等均为 Actor 内部私有模块。

### `command.rs`

定义 Actor 接收的消息协议，详见 [08-并发安全策略.md](08-并发安全策略.md)。

### `handle.rs`

调用方持有的客户端句柄，支持自动重连，可任意 `Clone` 跨线程传递：

```rust
#[derive(Clone)]
pub struct MemoryHandle {
    inner: Arc<RwLock<HandleInner>>,
}

enum HandleInner {
    Local { tx: mpsc::Sender<MemoryCommand> },
    Ipc { client: IpcClient },
}

impl MemoryHandle {
    /// 查询（async，等待响应）
    pub async fn load_injection(&self, session_id: &str, workspace_id: Option<&str>) -> Vec<String>;
    pub async fn recall(&self, anchors: RecallAnchors, limit: usize) -> Vec<RecallHit>;

    /// 写入（fire-and-forget，不阻塞）
    pub fn write_episode(&self, episode: Episode);
    pub fn run_micro_rumination(&self, turn_result: TurnResult);

    /// 启动与连接
    pub async fn connect_or_spawn(workspace_id: Option<String>, process_type: ProcessType) -> Result<Self>;

    /// 生命周期
    pub async fn shutdown(&self);
}
```

### `actor.rs`

Memory 独立运行时，串行处理所有命令：

```rust
pub struct MemoryActor {
    store: MemoryStore,    // 独占持有，无需锁
    cmd_rx: mpsc::Receiver<MemoryCommand>,
}

impl MemoryActor {
    pub fn spawn(workspace_id: Option<String>) -> Result<MemoryHandle>;
    async fn run(mut self);  // 事件循环
}
```

### `election/`

Leader 选举与迁移机制，详见 [08-并发安全策略.md](08-并发安全策略.md)。

### `ipc/`

跨进程通信层，UDS 服务端/客户端、帧协议、序列化。

### `types.rs`

所有 Memory 相关数据结构定义，详见 [01-记忆分层设计.md](01-记忆分层设计.md)。

### `store.rs`

替代现有 `tiangong-core/context/memory.rs`：

```rust

impl MemoryStore {

```

### `injection.rs`

三级注入读取，详见 [02-注入层设计.md](02-注入层设计.md)。

### `writer.rs`

Episode 写入器，接收 turn 执行结果，调用 lite 模型提取摘要。

### `recall.rs`

锚点提取和粗召回，详见 [03-渐进式回忆.md](03-渐进式回忆.md)。

### `rumination.rs`

三级反刍实现，详见 [05-反刍与反思层.md](05-反刍与反思层.md)。

## 与其他 crate 的集成点

### 各入口 crate 初始化

```rust
// tiangong-cli/src/main.rs
use tiangong_memory::{MemoryHandle, ProcessType};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let memory = tiangong_memory::start(workspace_id, ProcessType::Cli).await?;
    // 将 handle 传入 core
    let core = TiangongCore::new(memory.clone(), ...);
    core.run().await?;
    memory.shutdown().await;
    Ok(())
}
```

```rust
// tiangong-server/src/main.rs
use tiangong_memory::{MemoryHandle, ProcessType};

async fn main() -> anyhow::Result<()> {
    let memory = tiangong_memory::start(workspace_id, ProcessType::Server).await?;
    // Server 作为长期运行进程，最适合持有 Leader
    let core = TiangongCore::new(memory.clone(), ...);
    // ...
}
```

### tiangong-core 集成

#### 1. `prompt/sections.rs`

```diff
- pub fn build_user_context(session_id: &str) -> Vec<String> {
-     let store = MemoryStore::load_from_disk();
-     store.format_for_context(session_id)
- }
+ pub async fn build_user_context(
+     session_id: &str,
+     memory: &tiangong_memory::MemoryHandle,
+ ) -> Vec<String> {
+     memory.load_injection(session_id, None).await
+ }
```

#### 2. `prompt/assembler.rs`

```diff
  // PromptAssembler 持有 MemoryHandle（Clone 成本极低）
+ memory_handle: tiangong_memory::MemoryHandle,

  async fn assemble(&self, ...) -> AssembledPrompt {
      ...
      let user_context = build_user_context(session_id, &self.memory_handle).await;
+     let recall_context = self.memory_handle.recall(anchors, 10).await; // Phase C
      ...
  }
```

#### 3. `context/organizer.rs`

```diff
+ memory_handle: tiangong_memory::MemoryHandle,

  async fn compress_if_needed(&mut self, ...) {
      ...
+     self.memory_handle.run_meso_rumination(session_id, workspace_id);
  }
```

#### 4. `runtime.rs`（EventLoopRunner）

```diff
+ memory_handle: tiangong_memory::MemoryHandle,

  async fn on_turn_completed(&mut self, turn_result: &TurnResult) {
      ...
+     self.memory_handle.run_micro_rumination(turn_result.clone());
  }
```

> 所有集成点通过 `MemoryHandle` 通讯，不直接访问 `MemoryStore`。
> 写入类操作使用 fire-and-forget，不 `.await`，不阻塞主流程。

## 迁移策略

### `context/memory.rs` 的废弃

1. Phase A 完成后，`tiangong-memory/injection.rs` 完全替代 `MemoryStore::format_for_context()`
2. 将 `context/memory.rs` 中仍在使用的 utility 函数迁移到 `tiangong-memory/store.rs`
3. 标记 `context/memory.rs` 为 `#[deprecated]` 并在 Phase B 完成后删除

### 无需 feature flag

由于 Memory 是独立 crate，各入口直接在 Cargo.toml 中控制是否依赖即可。不需要 feature flag——Memory 是所有模式的必要基础设施，不允许关闭。
