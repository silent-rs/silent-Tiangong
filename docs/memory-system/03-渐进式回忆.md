# 03 - 渐进式回忆（Progressive Recall）

## 概述

Progressive Recall 是天工 Memory 的核心检索机制。核心思想：

> 不做一次性全量注入，而是从粗到细、按需展开。

## 工作流（5 阶段）

```
用户输入
  ↓
[Stage 1] 锚点提取 ─── 从当前 turn 提取关键词和意图
  ↓
[Stage 2] 粗召回 ───── 基于锚点在记忆索引上匹配 depth-1 摘要
  ↓
[Stage 3] 规划评估 ── Planner 结合粗召回结果决定是否需要展开
  ↓
[Stage 4] 定向展开 ── 对命中的条目加载 depth-2 结构化数据
  ↓
[Stage 5] 证据回放 ── 必要时加载 depth-3 原始证据
```

---

## Stage 1: 锚点提取

**输入**：当前 turn 的用户消息 + 最近 2 条消息

**输出**：`RecallAnchors`

```rust
#[derive(Debug, Clone)]
pub struct RecallAnchors {
    pub keywords: Vec<String>,
    pub intent: Option<String>,
    pub entity_refs: Vec<String>,   // 引用的实体名
    pub session_id: String,
    pub workspace_id: Option<String>,
}
```

**实现策略（Phase C 初期）**：

- **不使用 LLM 调用**（避免增加延迟），采用规则提取：
  1. 分词 → 提取名词/动词/专有名词
  2. 匹配已知实体名（Entity Memory 中的 `title`）
  3. 提取代码标识符（蛇形命名、驼峰命名等模式）

```rust
pub fn extract_anchors(
    messages: &[Message],
    known_entities: &[String],
    session_id: &str,
    workspace_id: Option<&str>,
) -> RecallAnchors {
    let text = messages.iter()
        .filter(|m| m.role == MessageRole::User)
        .map(|m| m.content.as_str())
        .collect::<Vec<_>>()
        .join(" ");

    let keywords = extract_keywords(&text);
    let entity_refs = known_entities.iter()
        .filter(|e| text.contains(e.as_str()))
        .cloned()
        .collect();

    RecallAnchors {
        keywords,
        intent: None, // Phase C+ 可加 LLM intent 分类
        entity_refs,
        session_id: session_id.to_string(),
        workspace_id: workspace_id.map(String::from),
    }
}
```

## Stage 2: 粗召回

**输入**：`RecallAnchors`

**输出**：`Vec<RecallHit>`，按相关性排序

```rust
#[derive(Debug, Clone)]
pub struct RecallHit {
    pub node_id: String,
    pub kind: MemoryKind,
    pub title: String,
    pub summary: String,         // depth-1
    pub relevance_score: f32,    // 0.0-1.0
}
```

**匹配算法**：

```rust
pub fn coarse_recall(
    anchors: &RecallAnchors,
    index: &MemoryIndex,
    limit: usize,
) -> Vec<RecallHit> {
    let mut hits: Vec<RecallHit> = index.nodes.iter()
        .filter(|node| {
            // 作用域过滤：只搜索当前 workspace 和 global
            match &node.scope {
                MemoryScope::Global => true,
                MemoryScope::Workspace { workspace_id } => {
                    anchors.workspace_id.as_deref() == Some(workspace_id)
                }
                MemoryScope::Session { session_id } => {
                    session_id == &anchors.session_id
                }
            }
        })
        .filter(|node| node.status == MemoryStatus::Active)
        .map(|node| {
            let score = compute_relevance(node, anchors);
            RecallHit {
                node_id: node.id.clone(),
                kind: node.kind.clone(),
                title: node.title.clone(),
                summary: node.summary.clone(),
                relevance_score: score,
            }
        })
        .filter(|hit| hit.relevance_score > 0.1) // 阈值过滤
        .collect();

    hits.sort_by(|a, b| b.relevance_score.partial_cmp(&a.relevance_score).unwrap());
    hits.truncate(limit);
    hits
}
```

**相关性计算**：

```rust
fn compute_relevance(node: &MemoryNode, anchors: &RecallAnchors) -> f32 {
    let mut score = 0.0;

    // 关键词匹配
    let keyword_matches = anchors.keywords.iter()
        .filter(|kw| {
            node.keywords.iter().any(|nk| nk.contains(kw.as_str()))
            || node.title.contains(kw.as_str())
            || node.summary.contains(kw.as_str())
        })
        .count();
    score += (keyword_matches as f32) * 0.3;

    // 实体引用匹配
    let entity_matches = anchors.entity_refs.iter()
        .filter(|e| node.title.contains(e.as_str()) || node.keywords.contains(e))
        .count();
    score += (entity_matches as f32) * 0.4;

    // 重要性加权
    score += node.importance * 0.2;

    // 时间衰减（新条目得分更高）
    score += recency_boost(&node.updated_at) * 0.1;

    score.min(1.0)
}
```

**Phase D+：引入向量检索**

当 Episode 数量超过阈值（如 200 条）时，关键词匹配效率下降。届时引入向量相似度作为辅助：

- 对每条 `MemoryNode.summary` 计算 embedding
- 用户输入 → embedding → 余弦相似度 top-k
- 与关键词匹配结果合并去重

技术选型见 [07-持久化格式与技术选型.md](07-持久化格式与技术选型.md)。

## Stage 3: 规划评估

**判定逻辑**：

Planner 在制定执行计划时，参考粗召回结果：

```rust
pub enum RecallDecision {
    /// 粗召回足够，直接用 depth-1 摘要注入 Prompt
    UseSummaries,
    /// 需要展开特定条目到 depth-2
    Expand(Vec<String>),  // node_ids
    /// 不需要历史记忆
    Skip,
}
```

判定规则（不使用额外 LLM 调用）：
- 粗召回 0 条 → `Skip`
- 所有命中 `relevance_score > 0.7` → `UseSummaries`
- 存在 `0.3 < relevance_score < 0.7` 的条目 → `Expand` 这些条目

## Stage 4: 定向展开

加载 `depth-2` 结构化数据：

```rust
pub fn expand_nodes(
    node_ids: &[String],
    store: &MemoryStore,
) -> Vec<ExpandedMemory> {
    node_ids.iter()
        .filter_map(|id| store.load_depth2(id).ok())
        .collect()
}

pub struct ExpandedMemory {
    pub node_id: String,
    pub full_content: serde_json::Value, // Episode/Decision/Entity 的完整结构
}
```

展开结果注入到 Prompt 的 UserContext 段：

```

- 结果: 成功
- 关键修改: 将 loop_context 消息角色从 System 改为 User
- 涉及文件: core/mod.rs, model.rs
```

## Stage 5: 证据回放

仅在执行阶段工具需要原始内容时触发。

**触发条件**：
- 工具调用涉及历史文件路径，且文件已变更
- 用户提问"当时为什么这样做"类问题

**实现**：
- 从 `evidence/` 目录读取引用的原始日志
- 截取相关片段（限制 1KB 以内）
- 注入到当前 turn 的附加上下文

## 性能约束

| 阶段 | 延迟预算 | 实现方式 |
|------|---------|---------|
| Stage 1 锚点提取 | < 5ms | 规则匹配，无 LLM |
| Stage 2 粗召回 | < 10ms | 内存索引扫描 |
| Stage 3 规划评估 | 0ms | 与 Planner 调用合并 |
| Stage 4 定向展开 | < 20ms | 文件 I/O |
| Stage 5 证据回放 | < 50ms | 文件 I/O，按需触发 |

**总延迟**：正常路径（Stage 1-4）< 35ms，不影响用户感知。
