# 09 - 分阶段落地路径

## 总体策略

遵循"最小可用 → 逐步增强"原则，每个阶段独立可交付、可验证。

---

## Phase A: Injection 层 + 独立 crate 骨架

**目标**：创建 `tiangong-memory` 独立 crate，实现 Actor 骨架 + 三级 Injection 读取。

**前置条件**：无

**代码变更**：

| 文件 | 变更类型 | 描述 |
|------|---------|------|
| `crates/tiangong-memory/Cargo.toml` | 新增 | crate 配置 |
| `crates/tiangong-memory/src/lib.rs` | 新增 | crate 入口，导出公共 API |
| `crates/tiangong-memory/src/types.rs` | 新增 | 基础类型定义（MemoryScope 等） |
| `crates/tiangong-memory/src/command.rs` | 新增 | MemoryCommand 消息协议 |
| `crates/tiangong-memory/src/handle.rs` | 新增 | MemoryHandle（客户端句柄，支持自动重连） |
| `crates/tiangong-memory/src/actor.rs` | 新增 | MemoryActor（独立运行时） |
| `crates/tiangong-memory/src/store.rs` | 新增 | MemoryStore（Actor 内部磁盘读写） |
| `crates/tiangong-memory/src/injection.rs` | 新增 | 三级 Injection 读取 |
| `crates/tiangong-memory/src/election/` | 新增 | Leader 选举骨架（进程内模式） |
| `Cargo.toml`（workspace） | 修改 | 添加 tiangong-memory 到 members |
| `crates/tiangong-core/Cargo.toml` | 修改 | 添加 tiangong-memory 依赖 |
| `prompt/sections.rs` | 修改 | `build_user_context()` 通过 Handle 查询 |
| `context/memory.rs` | 标记废弃 | `#[deprecated]` |

**预计代码量**：~300 行新增，~30 行修改

**验证标准**：
1. 创建 `~/.tiangong/memory/profile/agent.md` 后，新会话能注入其内容
2. 不创建文件时，行为与现有一致（空注入）
3. Memory Actor 正常启动和关闭，无泄漏
4. 所有入口（CLI、Server、GUI）都能成功初始化 Memory
5. `cargo check --workspace` 通过

**手动验证步骤**：
```bash
# 1. 创建 Profile Injection
mkdir -p ~/.tiangong/memory/profile
echo "# Profile\n- 默认使用简体中文" > ~/.tiangong/memory/profile/agent.md

# 2. 分别以 CLI、Server、GUI 模式启动天工，检查 Prompt 中是否包含 Profile 内容
# 3. 删除文件后确认无异常
```

## Phase B: Episodic Memory 写入 + IPC

**目标**：turn 执行完成后自动写入 Episode，实现跨进程 IPC 和 Leader 选举。

**前置条件**：Phase A 完成

**代码变更**：

| 文件 | 变更类型 | 描述 |
|------|---------|------|
| `tiangong-memory/src/store.rs` | 扩展 | MemoryStore + MemoryIndex 磁盘读写 |
| `tiangong-memory/src/writer.rs` | 新增 | EpisodeWriter（调用 lite 模型提取摘要） |
| `tiangong-memory/src/rumination.rs` | 新增 | MicroRumination（仅 Episode 写入部分） |
| `tiangong-memory/src/actor.rs` | 扩展 | 处理 WriteEpisode / RunMicroRumination 命令 |
| `tiangong-memory/src/ipc/` | 新增 | UDS IPC 服务端/客户端 |
| `tiangong-memory/src/election/` | 扩展 | Leader 选举、心跳、Follower 监控 |
| runtime 集成点 | 修改 | turn 完成后通过 Handle 发送反刍命令 |

**预计代码量**：~500 行新增，~50 行修改

**无新增外部依赖**（Actor 模型仅使用 tokio channel，IPC 使用 tokio UDS）

**验证标准**：
1. 执行一个包含工具调用的 turn 后，`~/.tiangong/memory/workspaces/<id>/episodes/` 下产生 Episode 文件
2. 纯对话 turn 不产生 Episode
3. Episode 文件内容合理（摘要简洁、keywords 准确）
4. 并发安全：Actor 串行处理，多个 turn 并发完成时不丢数据
5. 多进程场景：同时运行 GUI + CLI，只有一个 Leader，另一个通过 IPC 访问
6. Leader 进程退出后，剩余进程能自动选举新 Leader

**关键设计决策**：
- Phase B 的 Episode 采用“只写不读”策略
- 写入命令通过 Handle fire-and-forget，不阻塞主流程
- Actor 内部串行处理，天然无写入冲突
- IPC 和 Leader 选举是必要组件，确保多进程场景 Memory 不缺失

## Phase C: Progressive Recall

**目标**：实现锚点提取 + 粗召回 + 定向展开，Recall 结果注入 Prompt。

**前置条件**：Phase B 完成（有 Episode 数据可供召回）

**代码变更**：

| 文件 | 变更类型 | 描述 |
|------|---------|------|
| `tiangong-memory/src/recall.rs` | 新增 | RecallAnchors 提取 + 粗召回 + 展开 |
| `tiangong-memory/src/rumination.rs` | 扩展 | MesoRumination（Entity/Decision 提取） |
| `prompt/assembler.rs` | 修改 | 注入 Recall 结果到 Prompt |
| `context/organizer.rs` | 修改 | 压缩完成回调 Meso 反刍 |
| `workspace_index/` | 新增（可选） | 文件树索引 |

**预计代码量**：~500 行新增，~50 行修改

**验证标准**：
1. 新会话提问历史任务相关内容时，Recall 能命中相关 Episode
2. 锚点提取延迟 < 5ms
3. 粗召回延迟 < 10ms
4. Recall 结果正确注入到 Prompt 的 UserContext 段

---

## Phase D: Rumination + Workspace Index

**目标**：完整反刍机制、过时检测、符号索引。

**前置条件**：Phase C 完成

**代码变更**：

| 文件 | 变更类型 | 描述 |
|------|---------|------|
| `tiangong-memory/src/rumination.rs` | 扩展 | MetaRumination（过时检测、归档） |
| `workspace_index/file_tree.rs` | 新增 | 文件树扫描与增量更新 |
| `workspace_index/symbol_index.rs` | 新增 | tree-sitter 符号提取 |
| 向量搜索集成 | 新增（可选） | usearch 或类似库 |

**预计代码量**：~800 行新增，~100 行修改

**新增依赖（可选）**：
```toml
tree-sitter = "0.24"      # 符号提取
tree-sitter-rust = "0.23"  # Rust 语法
usearch = "2"              # 向量搜索（如需）
```

**验证标准**：
1. 应用启动时自动执行 Meta 反刍
2. 过时 Episode 被正确标记
3. 文件树索引在 turn 中可用
4. 符号索引准确（Rust 文件的 struct/fn/mod）

## 阶段依赖图

```
Phase A (Injection)
    ↓
Phase B (Episode Write)
    ↓
Phase C (Recall + Meso)
    ↓
Phase D (Meta + Index)
```

每个阶段可独立发布，不依赖后续阶段的实现。

---

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Episode 提取质量差 | 记忆数据噪声大 | Phase B 只写不读，后续人工审查后调优 prompt |
| 向量搜索引入编译依赖 | 构建时间增长 | Phase D 可选，先用关键词匹配 |
| LLM 提取成本 | API 费用增加 | 使用 lite 模型，每次 < 1000 tokens |
| Memory 目录膨胀 | 磁盘空间 | Meta 反刍归档 + Evidence 定期清理 |
| Leader 选举复杂度 | 开发成本 | Phase A 先实现进程内模式，Phase B 完善跨进程选举 |
